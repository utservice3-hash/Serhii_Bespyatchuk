## Логіка передачі лідогена менеджеру

Тригер: вебхук `Статус сделки изменен`, обробляється в
`_process_status_change()` (app.py), коли `pipeline_id == 8921928` і
`status_id == 69716164`.

Виняток: якщо `old_status_id` входить у `SKIP_FROM_STATUSES`
(69693652, 69693656, 69693660, 70419108) — це повторний прохід у межах
кваліфікації, не нова передача, сповіщення й запис у Sheets не йде.

⚠️ Цей `SKIP_FROM_STATUSES`-виняток діє **лише** на вебхуку `Статус сделки
изменен` (там `old_status_id` є в payload). На окремому вебхуку `Отв-й
сделки изменен` (зміна лише відповідального без руху по етапу)
`old_status_id` **недоступний** — Kommo не віддає його ні в payload, ні
через `GET /leads/{id}`. Тож там виняток не оцінюється; від дубля страхує
власний дедуп `_handle_new_lead` (`pending` + `_notified_new_leads`).

`_handle_new_lead()`:
1. Дедуп — лід уже в `pending` або в `_notified_new_leads`
   (TTL `_NEW_LEAD_DEDUP_SECONDS`) → пропустити (Kommo шле дублюючі
   вебхуки на одну подію).
2. Записати в `pending[lead_id]` (черга "очікує дзвінка").
3. Надіслати в Telegram (команда менеджера, лише робочі години):
   `📥 Нова заявка від лідогенератора` з ім'ям менеджера, назвою ліда,
   джерелом, лінком.
4. Записати рядок у Google Sheets, лист **"Реєстр"** —
   `sheets.append_transfer()`.

Подальший трекінг, поки лід у `pending`:
- `_check_overdue_leads()` (кожні 5 хв, робочі години) — якщо немає
  дзвінка ≥20 хв (`REMINDER_MINUTES`), нагадування кожні 20 хв у групу,
  з тегом менеджера й керівника (`SUPERVISOR_MAP`).
- Дзвінок зафіксовано (`_handle_call`) → `pending.pop()`, запис часу
  першого дзвінка в Sheets.
- Перехід у "Лід взятий у роботу" (69693652) → `_handle_taken()` —
  запис часу взяття в Sheets.

## Google Sheets — лист "Реєстр"

Один рядок = одна передача лідогена. Колонки:

| # | Колонка | Заповнюється |
|---|---|---|
| 1 | Lead ID | при передачі |
| 2 | Назва ліда | при передачі |
| 3 | Менеджер | при передачі |
| 4 | Команда | при передачі |
| 5 | Час передачі | при передачі (`append_transfer`) |
| 6 | Час взяття в роботу | пізніше (`update_taken`) |
| 7 | Перший дзвінок | пізніше (`update_first_call`) |
| 8 | Час реакції (хв) | = взяття − передача |
| 9 | Час до дзвінка (хв) | = дзвінок − передача |

**Важливо:** перехід у статус "ВЗЯТО НА ПРОРАХУНОК" (69693668,
пайплайн Перевозки) НІЯК не пишеться в Sheets і не обробляється ботом
взагалі — лист "Реєстр" стосується лише етапу кваліфікації/передачі,
не самого прорахунку. Якщо знадобиться рахувати "передані прорахунки"
як окрему метрику — це треба додавати окремо (новий webhook-обробник
для статусу 69693668 пайплайну 8921932 + новий запис/колонка).

### Як рахувати «Нова заявка від лідогенератора»

Одна «заявка від лідогенератора» = один перехід ліда у статус
`NEW_FROM_LIDOGEN` (69716164, воронка Кваліфікація 8921928), зафіксований
`_handle_new_lead()`. Кожна така подія пише **один рядок в аркуш «Реєстр»**
(`sheets.append_transfer`).

**Джерело правди для підрахунку — аркуш «Реєстр», а НЕ in-memory лічильники.**
Подія паралельно потрапляє у три місця, але для рахунку годиться лише перше:

| Місце | Персистентність | Для підрахунку |
|---|---|---|
| Аркуш «Реєстр» | ✅ персистентно | **так — рахуй звідси** |
| `pending[lead_id]` | in-memory, гине при рестарті | ні (лише черга нагадувань) |
| `_stats_log` (→ `_write_daily_snapshot` 23:55, `_build_stats_text`) | **in-memory, обнуляється при кожному деплої Render** | ні — після деплою серед дня цифри неповні |

Правила підрахунку по «Реєстру»:
- **Кількість за період** = кількість рядків, де «Час передачі» (кол. 5,
  формат `YYYY-MM-DD HH:MM:SS`) потрапляє в період.
- **По менеджеру / команді** — фільтр по колонках 3 / 4.
- Кожен рядок унікальний по Lead ID — дублі бот уже відсіює (дедуп
  `pending` + `_notified_new_leads` 5 хв), тож рядки не задвоюються.
- **Повторні проходи не рахуються:** якщо лід зайшов у 69716164 з робочого
  етапу (`SKIP_FROM_STATUSES`) — `_handle_new_lead` пропускає його, рядка в
  «Реєстрі» не буде.
- «Час реакції» = взяття − передача (хв); «Час до дзвінка» = перший
  дзвінок − передача (хв). Порожньо = ще не взяли / не дзвонили.

⚠️ Telegram-сповіщення `📥 Нова заявка від лідогенератора` шлеться лише в
робочі години, АЛЕ рядок у «Реєстр» пишеться завжди (і поза годинами) —
тож рахуй по аркушу, а не по кількості повідомлень у Telegram.

## Плани менеджерів/команд — з Google Sheets (не з коду)

Щомісячні плани більше НЕ хардкодяться в код. Джерело правди — два
аркуші основної таблиці:
- **«Плани менеджерів»**: `user_id | Менеджер | Команда | План (грн)`
  (рядок без валідного user_id ігнорується — так можна тримати людей
  без акаунта в Kommo, напр. Крістіна Захарченко);
- **«Плани команд»**: `Команда | План (грн)`.

`_refresh_plans_from_sheet()` (app.py) читає їх через `sheets.read_plans()`
і мутує `MANAGER_PLANS`/`TEAM_PLANS` **на місці** (`clear`+`update`, щоб усі
посилання бачили зміни); `MANAGER_TEAM` лише доповнюється (видалення рядка
з таблиці не ламає роутинг сповіщень). Запуск: на старті сервісу, щодня о
06:00 Київ, вручну — `GET /refresh-plans`. Якщо таблиця/аркуш недоступні —
тихо лишаються значення, зашиті в коді (стартовий фолбек).

Первинне заповнення аркушів поточними значеннями з коду:
`GET /seed-plans-sheet?confirm=1` (перезаписує аркуші!). Далі таблицю веде
людина: новий місяць = поміняти цифри в таблиці, деплой не потрібен.

## Часова зона

Весь «київський час» (робочі години сканера, черговий вихідного дня,
усі cron-звіти) рахується через `Europe/Kyiv` (`KYIV_TZ` в app.py,
scheduler з `timezone="Europe/Kyiv"`), а НЕ фіксований UTC+3 — переведення
годинників (взимку UTC+2) враховується автоматично. Не повертати фіксовані
offset-и: взимку все з'їде на годину.

### Доставка повідомлень — userbot (Telethon), а НЕ Bot API

⚠️ Ключове: повідомлення в групі шле бот `TransNowBot`, а **Telegram Bot
API за дизайном не доставляє боту повідомлення, надіслані іншим ботом**
(навіть якщо наш `@utsuser01_bot` — адмін групи; адмінство знімає privacy
mode лише для повідомлень людей). Тому шлях через `/tg-update` ловить лише
випадки, коли повідомлення TransNowBot **переслала людина** (форвардом).

Для автоматичного читання використовується **userbot на Pyrogram**
(`elogist_userbot.py`) — звичайний юзер-акаунт, що є учасником групи й
бачить усі повідомлення, включно з ботовими. Він викликає той самий
`_handle_elogist_message()`. (Pyrogram, а не Telethon, бо залежність
Telethon `pyaes` не збирається на новому setuptools і ламає деплой Render;
Pyrogram+TgCrypto ставляться з готових wheel.)

- Конфіг через env: `TG_API_ID`, `TG_API_HASH`, `TG_SESSION` (StringSession).
  Без них слухач тихо не стартує (фолбек — лише `/tg-update`).
- `TG_SESSION` генерується локально один раз: `scripts/elogist_login.py`
  (логін під акаунтом, що Є В ГРУПІ; вивід вставити в Render env).
- Слухач стартує на рівні модуля поряд зі scheduler
  (`elogist_userbot.start_listener(_handle_elogist_message)`), у фоновому
  треді з власним asyncio-loop і автоперепідключенням кожні 30 с.
- Procfile: `--workers 1`, тож слухач один — дублів між воркерами немає.

Обробка тексту (спільна для userbot і `/tg-update`):

`/tg-update` (app.py) перевіряє `message.chat.id == ELOGIST_SOURCE_CHAT_ID`
і передає текст у `_handle_elogist_message()`:
1. `_parse_elogist_message()` — витягує телефон (regex) і, якщо є,
   маршрут з першого рядка. Без телефону — повідомлення ігнорується.
2. Дедуп по телефону (заявка в СРМ має прийти лише один раз, дублі
   ігноруємо), два рівні:
   - in-memory кеш на `ELOGIST_DEDUP_MINUTES` (30 хв) — швидка перевірка
     повторних спрацювань форми;
   - CRM-перевірка `kommo.find_recent_lead_by_phone(phone, hours=24)` —
     пошук по query за останніми 9 цифрами телефону: якщо за останню добу
     лід із цим телефоном уже створено, дубль пропускаємо. Це страхує від
     втрати in-memory кешу при рестарті Render (деплой/перезапуск).
3. `kommo.create_lead_with_phone()` — створює контакт окремим запитом
   (Kommo не дозволяє inline-створення нового контакту разом зі
   створенням ліда, лише прив'язку вже існуючого `contact_id`), потім
   лід у пайплайні Кваліфікація (8921928), статус **"Дзвінки з сайту"**
   (69693660), з тегом `eLogist`. Назва ліда — маршрут, якщо є, інакше
   телефон.
4. Лід створюється без відповідального (Kommo автоматично підставляє
   власника токена як `responsible_user_id`, що збігається з
   `ADMIN_USER_ID`) — тож вже наявна логіка "Нерозібрана заявка"
   (нижче) підхоплює його сама, окремого сповіщення тут не потрібно.

### Окремий етап у Кваліфікації для eLogist

eLogist-ліди (і з userbot, і з веб-хука) створюються на власному етапі
**«Заявки eLogist (сайт)»** (`ELOGIST_STATUS = 108581472`, воронка
Кваліфікація 8921928) — щоб їх було видно окремо й рахувати конверсію по
тегу `eLogist`. Етап додано в `UNASSIGNED_STATUSES` (тож «нерозібрана
заявка» його підхоплює), а права на нього віддзеркалені з «Дзвінки з сайту»
для ролей Тимлид/Менеджер/Лідогенератор/Менеджер РПК (інакше рухати ліда
зміг би лише адмін — нове status_rights не додається автоматично). Конверсію
eLogist рахуємо фільтром по тегу `eLogist` через воронку (як рекламні звіти).

### Прямий веб-хук `/elogist-hook` (без Telegram)

Альтернатива userbot-у, якщо джерело (лендинг/eLogist) уміє слати заявку
на URL: `GET|POST /elogist-hook?token=<ELOGIST_HOOK_TOKEN>`. Приймає дані у
JSON, form або query; телефон бере з полів (`phone`/`tel`/`телефон`/…) або
regex по всьому тілу; маршрут — з `route`/`name`/… Далі та сама спільна
`_create_elogist_lead()` (дедуп + створення в кваліфікації, статус «Дзвінки
з сайту», тег `eLogist`). Захист — секретний `token` у URL (інакше 403).
Не потребує ні userbot, ні сесій — джерело просто POST-ить сюди заявку.

### Мітка джерела ліда в сповіщеннях (UTS / eLogist)

У всіх сповіщеннях про нерозібрану заявку (скан, веб-хук, нагадування 15/30хв,
ескалація 45хв) і в повідомленні «✅ Взято в роботу» додається рядок-мітка
`📨 Джерело ліда: eLogist` або `📨 Джерело ліда: UTS`. Визначення — helper
`_detect_elogist(lead, status_id)`: eLogist, якщо етап = `ELOGIST_STATUS`, або
є тег `eLogist`, або назва починається з «eLogist». Ознака зберігається в
`unassigned[lead_id]["is_elogist"]`, тож «Взято в роботу» показує те саме
джерело, що й початкова заявка. Мітку будує `_source_badge(is_elogist)`.

## Перший дотик по рекламних лідах (контроль озвучення ціни)

Мета: по кожному рекламному ліду команд РНК (Дарина=Михальчевська,
Андрій=Безпам'ятний) на ПЕРШОМУ дзвінку менеджер має озвучити ціну й
відпрацювати заперечення; контролюємо це автоматично.

Тригер: `_handle_call()` на кожен дзвінковий note запускає
`_handle_first_touch()` у фоновому треді. Той сам гейтиться:
1. Команда відповідального ∈ `FIRST_TOUCH_TEAMS` (РНК) — інакше вихід.
2. `kommo.has_utm_campaign(lead)` — лід з реклами (геомітка/utm),
   інакше вихід.
3. Перший **ВХІДНИЙ** дзвінок (note_type 10/`call_in`) тривалістю
   ≥ `FIRST_TOUCH_MIN_DURATION` (40с) — це і є "перший дотик". Вихідні
   дзвінки менеджера НЕ рахуються (перший дотик = клієнт сам зателефонував
   нам уперше). Дедуп дворівневий: in-memory `_first_touch_done` (швидкий)
   + **маркер-нотатка в CRM** `FIRST_TOUCH_MARKER` («🤖 AI: перший дотик
   проаналізовано») — переживає рестарт Render, без неї бот після деплою
   повторно транскрибував би той самий дзвінок. Нотатка пишеться після
   аналізу (з результатом — його видно тімліду прямо в угоді), перевірка —
   по вже завантажених нотатках ліда (безкоштовно). «Зайняття» ліда в
   `_first_touch_done` (перевірка + `add`) — атомарне під `_state_lock`, щоб
   два близькі дзвінкові вебхуки не дали дві транскрибації (платний Groq) і
   дубль-сповіщення.
   **Дедуп по КЛІЄНТУ (номеру), а не лише по угоді (правило: тільки перший
   контакт).** Перший дотик аналізуємо **один раз на контакт**; повторні
   дзвінки того самого номеру — навіть якщо це вже ІНША угода — не
   аналізуються на озвучення ціни. Ключ — головний контакт ліда
   (`kommo.get_lead_main_contact_id`, той самий номер = той самий контакт).
   Перед транскрибацією: спершу in-memory `_first_touch_contacts`, потім
   персистентний маркер `FIRST_TOUCH_MARKER` на нотатках **контакту**
   (`kommo.contact_has_note_marker`) — переживає рестарт і спільний для всіх
   угод контакту. Маркер на контакт (і додавання в set) пишемо ЛИШЕ після
   реально відправленого аналізу — щоб перший спам/не-транспортний дзвінок не
   заблокував майбутній реальний перший дотик того самого клієнта. Маркер на
   самому ліді лишається як і був (дедуп по угоді + видно тімліду).
4. Транскрибація (Groq) → `ai_analyzer.analyze_first_touch()` повертає
   `about_transport` / `price_voiced` / `objections_handled` +
   **`weakness`** (одна конкретна слабка сторона дзвінка) і **`reco`**
   (конкретна дія на майбутнє, щоб недолік не повторювався). У сповіщенні
   показуються окремими рядками `⚠️ Слабка сторона:` і `🔧 Наступного разу:`
   (замість загального підсумку) — щоб розбір був дієвим, а не описовим.
   Якщо розмова НЕ про перевезення (`about_transport=False`) — пропуск
   (спам/не релевант не рахується).
5. Сповіщення в гілку команди (`notifier.send_to_first_touch`):
   Михальчевська → чат -1002925017503, гілка 7689; Безпам'ятний →
   -1002258732695, гілка 14232. Заголовок: ✅/❌ ціну озвучено.
6. Подія пишеться в `_first_touch_log` (in-memory, по днях).

Щоденне зведення: `_send_first_touch_admin_report()` о 18:00 Київ
(scheduler з `timezone="Europe/Kyiv"`, тож 18:00 місцевого цілий рік —
не фіксований UTC) → `notifier.send_to_admin_stats` (чат -1004407179676,
гілка 6): скільки прийнято рекламних лідів (перший дотик) і скільки з них
з озвученою ціною, з розбивкою по командах.

⚠️ Бот має бути учасником адмінської групи -1004407179676.
⚠️ `_first_touch_log` — in-memory: редеплой серед дня скидає денне зведення
(сам дедуп аналізу тепер персистентний через CRM-нотатку).

**Персистентний облік + звіт за період.** Кожен проаналізований перший дотик
пишеться рядком в аркуш Google Sheets **«Перший дотик»**
(`sheets.append_first_touch`, поряд із записом у `_first_touch_log`): колонки
`Дата | Час | Менеджер | Команда | Lead ID | Ціну озвучено | Заперечення
відпрацьовано | Розмова про перевезення`. Звіт за будь-який період читається
**з таблиці, БЕЗ жодного запиту до Kommo**: `GET /first-touch-report?days=7`
(`sheets.read_first_touch` → total / priced / розбивка по командах).
Причина: рахувати ретроспективно по маркер-нотатках лідів = сотні запитів до
Kommo (перебір нотаток), що ризикує лімітом; аркуш це усуває. Аркуш
наповнюється з моменту деплою цієї фічі (історію до неї він не містить).

## Перевірка закриття угоди як "Дубль"

Коли угоду закривають зі статусу 143 (в обох пайплайнах) з причиною
відмови, що містить "дубл" (`kommo.get_reject_reason()`), менеджер за
правилом має вказати в примітках **#ID активної угоди** (або повне
посилання `leads/detail/<id>`).

`_check_duplicate_reference()` (app.py, у фоновому треді на статус 143):
1. Бере причину відмови; якщо це не дубль — виходить.
2. Збирає текст усіх текстових приміток (`note_type` 4/common) і шукає
   `#<id>` або `leads/detail/<id>` (5–9 цифр), виключаючи ID самої угоди.
3. Якщо знайдено посилання на іншу активну угоду — лише лог, нічого не
   шле. Якщо ID немає — `⚠️ Угоду закрито як дубль без ID активної угоди`
   у групу команди менеджера (`send_to_team_group`) з тегом менеджера й
   тімліда — нагадування додати ID.

Додатково — у `_handle_closed_not_realized` (Перевозки): якщо причина —
**дубль**, то навіть коли AI-вердикт `ПЕРЕДЧАСНЕ`, угоду **НЕ повертають**
у роботу (дубль = легітимне закриття). У сповіщенні замість блоку «на
допрацювання» показується `🔁 Дубль — угоду не повертаємо в роботу` з
посиланням на активну угоду (`_find_active_deal_ref` — знаходить #ID/лінк
у нотатках) або попередженням, що посилання відсутнє й його треба додати.

Так само причина, що містить **"тест"** (`is_test`), — легітимне
закриття: угоду **НЕ повертають** у роботу навіть при вердикті
`ПЕРЕДЧАСНЕ`. У сповіщенні показується `🧪 Тест — угоду не повертаємо в
роботу`. Прапорці об'єднані в `no_return = is_duplicate or is_test`, який
і гейтить переміщення в «Повернуто АІ».

## Повернення угод AI у воронку "Продаж повний цикл"

> **Прапорець `QC_RETURN_ENABLED` (app.py) — зараз `True`.** Коли `False` —
> AI **НЕ переводить** угоди в «Повернуто АІ». Коли `True` — повертає лише
> за реальним приводом (див. правила нижче).

### Хто піддається AI-аналізу: ЛИШЕ РНК. РПК звільнені.

AI-аналіз закриття й повернення угод стосується **тільки команд РНК**
(Михальчевська/Безпам'ятний). Угоди, які закриває **РПК** (Яцик, Дмитрук,
Шаврова, Тендерний) або менеджер без відомої команди — **не піддаються**
ні AI-аналізу, ні поверненню, ні сповіщенням. Гейт `if team not in RNK_TEAMS:
return` стоїть на початку `_handle_closed_not_realized` (до будь-яких важких
запитів) і в `_check_non_target_lead`.

### Тегування/сповіщення (для РНК): тільки коли є привід повертати

Головне бізнес-правило (щоб бот не спамив): **бот сповіщає й тегує менеджера +
тімліда ЛИШЕ коли угоду повертають на допрацювання.** Коректне закриття
(вердикт `ОБ'ЄКТИВНЕ`), дубль, тест, або угода, що вже поверталась — **тихо**:
жодного повідомлення в Telegram, лише лог + запис у аркуш закритих угод.
Раніше `_handle_closed_not_realized` слав повідомлення з тегами на КОЖНЕ
закриття (і навіть для РПК) — тепер ні.

### Перевезення «По місту» — повний ігнор

Якщо поле «Тип запиту» (`2097965`) = «По місту» (`enum 6345143`,
`kommo.is_city_transport`) — угода **повністю ігнорується**: без AI-аналізу,
без повернення, без сповіщень (перевезення по місту без маржі ніде не
світимо). Гейт стоїть на початку `_handle_closed_not_realized` і
`_check_non_target_lead`.

### Рішення про повернення — по ПОВНІЙ картині, а не лише причині

`_gather_deal_context(lead_id)` збирає для AI: **тексти всіх нотаток CRM +
транскрипти всіх дзвінків** (з аркуша «Дзвінки РНК», відсутні —
дотранскрибовуються, з обмеженням) + **статистику спроб контакту** (к-сть
дзвінків, у скільки різних днів). `ai_analyzer.analyze_closed_deal` за цим
контекстом і **правилами якості** повертає `CLOSURE` (ПЕРЕДЧАСНЕ/ОБ'ЄКТИВНЕ) +
`RULE` (яке правило спрацювало) + `CATEGORY` + `NEXTSTEP`. Правила закриття:
1. **Немає зв'язку** — <3 спроб / не в різні дні / без коментарів → повертаємо.
2. **«Дорого»** — закрито після першої цінової відмови без відпрацювання +
   альтернатив + повторного контакту → повертаємо. (Не стосується «по місту».)
3. **«Неактуально»** — «пізніше/поки не треба» ≠ закриття → повертаємо; АЛЕ
   угоду, що переноситься 3-4 міс, не повертаємо.
4. **Інший перевізник** — не зафіксовано причину/можливість повернути → повертаємо.
5. **Вантаж скасовано** — якщо лише перенесли → повертаємо.
6. **Обов'язково для всіх причин** — коментар з причиною + опис дій + наступний
   крок; немає → повертаємо.
Якщо менеджер відпрацював якісно (достатньо контактів, є підтвердження, робота
в CRM) — закриття `ОБ'ЄКТИВНЕ`, не повертаємо (мета — контроль якості, а не
повернення всіх програних угод).

**Повага до правок тімліда (анти-цикл):** якщо угода вже має тег «Повернуто АІ»
(`already_returned`) — бот **не повертає повторно** (рішення тімліда головніше).

> _Скріншоти переписок (vision) — Фаза 2, ще не реалізовано._

Коли AI повертає угоду (вважає закриття помилковим/передчасним) — і для
**«не цільові»** (`_check_non_target_lead`, `is_target=True`), і для
**«закрито не реалізовано»** (`_handle_closed_not_realized`, вердикт
`ПЕРЕДЧАСНЕ`, окрім дублів) — угода **переводиться у воронку Перевозки =
Продаж повний цикл (8921932)** на етап **«Повернуто АІ Відділ якості (на
допрацювання)»** (`RETURNED_QC_STATUS = 108361876`, створений на початку
воронки) і тегується **«Повернуто АІ»** (`RETURNED_QC_TAG`).

Робиться це `kommo.move_lead_to(lead_id, pipeline_id, status_id, add_tag)`
одним PATCH: змінює pipeline+status і додає тег БЕЗ видалення наявних
(бере поточні теги за id і додає новий за name). **Захист:** якщо pre-fetch
`GET /leads/{id}` впав (таймаут/5xx → `None`), функція переміщає лід **без
`_embedded.tags` взагалі** — інакше з порожнім baseline PATCH стер би всі
наявні теги клієнта (`_embedded.tags` замінює весь набір). Тег тоді просто
не додається цього разу (додасться при наступному русі).

> **Винятки в `_check_non_target_lead` (гілка «Не цільові»).** Раніше
> виняток для дублів був лише в `_handle_closed_not_realized` (статус 143),
> а «нецільова» гілка повертала будь-що, де в дзвінках було перевезення —
> через що легітимні **дублі** (закриті як «Не цільові» з причиною «Дубль»
> і посиланням на активну угоду) помилково поверталися. Тепер до
> транскрибації стоять два ранні гейти:
> 1. **Дубль/Тест** — якщо причина відмови містить «дубл» або «тест», не
>    повертаємо (той самий `no_return`, що й у closed-not-realized).
> 2. **Захист від зациклення** — якщо угода вже має тег «Повернуто АІ»
>    (уже поверталась), не повертаємо повторно. Інакше AI воює з тімлідом:
>    той рухає угоду назад у «Не цільові», а AI за секунди повертає її.

Раніше повертали через `update_lead_status(TAKEN_TO_WORK)` — це лишало
угоду у старій воронці (а для «закрито не реалізовано» ще й ставило
QUAL-статус у PEREVOZY-ліда), через що тімлід не міг вести її в повному
циклі. Тепер угода одразу в правильній воронці з видимим тегом і етапом.

**Детальний AI-розбір у нотатки угоди.** При поверненні бот пише текстову
нотатку в картку Kommo (`kommo.add_note`): чому повернуто (`verdict_reason`),
категорія, наступний крок (`NEXTSTEP` — окреме поле в промпті
`analyze_closed_deal`, конкретна дія менеджеру), на що звернути увагу
тімліду (`teamlead_tip`) і повний розбір по 5 критеріях. Для «не цільових» —
чому помилково закрито + наступний крок.

**Права ролей на воронку (ВАЖЛИВО).** Ролі «Менеджер» (657568) і «Тимлид»
(657564) мають ГРАНУЛЬОВАНІ `status_rights` по етапах. У Kommo це означає:
що не вписано явно — заборонено. Новостворений етап/воронка автоматично НЕ
отримує прав для ролей → рухати може лише адмін. Тому після створення етапу
108361876 ролям «Менеджер» і «Тимлид» через API додано `edit:A/view:A` на
всі робочі етапи воронки 8921932 (окрім Incoming 69693664 — інший формат
без `export`; `delete` лишено `D`). Якщо створюватимеш нові етапи/воронки,
які мають рухати менеджери — не забудь додати права ролям.

## Сповіщення про нерозібрані/застряглі ліди в кваліфікації

Три незалежні механізми, всі виключають статус `70419108` (Дзвінки на
мобільні) за бізнес-правилом "стосується усіх етапів окрім дзвінки на
мобільні":

1. **`_scan_unassigned_leads()` / `_check_unassigned_leads()`** (кожні
   15 хв, 09:00–18:30 Київ) — сканує `UNASSIGNED_STATUSES` (всі етапи
   кваліфікації окрім 70419108 і фінальних 142/143) на ліди без
   реального відповідального (`responsible_id == 0` або
   `ADMIN_USER_ID`). Шле `📬 Нерозібрана заявка!` одразу + нагадування
   на 15/30 хв + ескалацію `🔴` на 45 хв (одноразово) — у групу РНК і
   ВСІ team-гілки трекінгу РНК.
   **Одне повідомлення на заявку, що редагується по місцю (без спаму).**
   Початкове сповіщення шлеться через `notifier.send_unassigned_tracked()`,
   який повертає `{chat_id, message_id}` кожного повідомлення →
   зберігаються в `unassigned[lead_id]["msg_refs"]`. Далі:
   - нагадування 15/30 хв і ескалація 45 хв **не шлють нових** повідомлень,
     а `notifier.edit_tracked()` **редагують те саме** (оновлюють час /
     позначку 🔴);
   - при взятті в роботу те саме повідомлення редагується на
     `✅ Взято в роботу (менеджер, X хв)` — спільна `_mark_lead_taken()`,
     яку викликають **три** шляхи: вебхук зміни статусу
     (`_process_status_change`), вебхук зміни відповідального (лід можуть
     взяти зміною ЛИШЕ відповідального без руху по етапу — цей вебхук
     приходить окремо), і самозцілення в `_check_unassigned_leads` (перед
     нагадуванням кожен лід звіряється з CRM: якщо відповідальний уже є —
     mark taken; якщо етап посунули без менеджера — тихо прибираємо з черги).
   Тобто в гілці лишається один слід на заявку, що еволюціонує:
   `📬 Нерозібрана → 🔴 45хв → ✅ Взято`. Редагування **власних**
   повідомлень бота **не потребує** прав адміна (на відміну від видалення).
   `delete_tracked()` лишено в notifier як утиліту, але не використовується.
   **Персист через CRM-нотатки:** після надсилання початкового сповіщення
   в лід пишеться маркер-нотатка `UNASSIGNED_NOTE_MARKER` з JSON
   `tg-refs: [{chat_id, message_id}]`. Після рестарту (деплой) скан
   знаходить лід, бачить маркер → відновлює `msg_refs` БЕЗ повторного
   надсилання (дублів у TG немає), редагування далі працюють. При взятті
   в роботу пишеться друга нотатка `UNASSIGNED_TAKEN_MARKER` — вона
   «гасить» стару refs-нотатку (відновлення дивиться, яка новіша), тож
   повторне падіння ліда в нерозібрані сповістить заново.
   У всіх повідомленнях циклу є рядок `📨 Джерело ліда: UTS|eLogist`
   (див. розділ eLogist).
   **Захист від одночасності:** CRM-нотатки страхують від дублів після
   *рестарту*, але не від *одночасного* спрацювання скану й вебхука на той
   самий лід. Тому «зайняття» слота в `unassigned` — атомарне під спільним
   `_state_lock` (перевірити `lid in unassigned` + одразу вставити запис у
   тому ж критичному секторі, і в `_scan_unassigned_leads`, і в
   `_handle_unassigned`). Так на одну заявку йде рівно одне сповіщення навіть
   при збігу мілісекунд. Мережеві виклики (GET, надсилання) — поза локом.
   Нагадування/ескалація мутують запис через посилання `info`, а не
   `unassigned[lid]`, щоб паралельний `pop` (взяття в роботу) не давав
   `KeyError`, що обірвав би решту проходу циклу.
2. **`_process_status_change()` webhook-шлях** — те саме правило
   `UNASSIGNED_STATUSES`, миттєва реакція на зміну статусу, а не
   періодичний скан.
3. **`_check_stale_qualification_leads()`** (раз на годину, робочі
   години) — `ACTIVE_QUAL_STATUSES` (всі "активні" етапи кваліфікації,
   включно з етапом eLogist `ELOGIST_STATUS`; теж без 70419108 і без
   NEW_FROM_LIDOGEN/фіналів) — ліди без руху `STALE_QUAL_DAYS` (2 дні) і
   більше, НАВІТЬ якщо вже є реальний відповідальний. Шле `🕒 Лід без руху N дн.` у командну групу
   менеджера, не частіше ніж раз на `STALE_QUAL_REMINDER_HOURS` (24 г).

## Звіт по рекламних кампаніях (щоп'ятничний + `/send-ad-report`)

- Джерело: `kommo.get_weekly_ad_campaign_report()` — ліди пайплайнів
  Кваліфікація+Перевозки за період, згруповані по UTM-кампанії.
- Маржа/виручка рахується по `REVENUE_STATUS_IDS` (з "АВТО ПРАЦЮЄ" і
  далі), не лише по "Успіх".
- WoW-порівняння — `prev_report` за попередній рівний період
  (`offset_days=days`).
- Тренд за 12 тижнів — `get_campaign_trend()`: КОЖЕН тиждень окремим
  запитом (`offset_days=week_index*7`), бо один великий запит на весь
  діапазон впирається в пагінацію Kommo (40 сторінок × 250 =
  10 000 лідів) і обрізає найновіші тижні.
- Повторні клієнти — `get_repeat_customers()`: серед лідів зі статусом
  "Успіх" за період бере унікальні `contact_id`, для кожного через
  `_count_contact_won_deals()` рахує всі минулі виграні угоди.
  **Важливо:** `filter[contacts][0]=<id>` на `/api/v4/leads` ігнорується
  Kommo API (підтверджено: фейковий contact_id повертає той самий
  результат) — реальний шлях: `GET /api/v4/contacts/{id}?with=leads`
  → список lead_id → пакетний запит `filter[id][]=...` для перевірки
  pipeline/status.
- Excel-білд і 12-тижневий тренд — важкі (60–90с), тому завжди йдуть у
  фоновому daemon-треді, інакше gunicorn `--timeout 60` рве запит.
  Помилки фону пишуться в `_last_ad_report_error`, перевірити —
  `GET /last-ad-report-error`.

## Ліміт запитів Kommo API (throttle + кеш)

Kommo блокує акаунт за перевищення ліміту (**~7 запитів/сек на акаунт**,
спільний на ВСІХ споживачів токена: наш бот, веб-UI, мобільний застосунок,
Ringostat тощо — усі під власником токена id 904923 = Admin). Тому бот
мінімізує власну частку:

- **Глобальний throttle + адаптивний backoff** (`kommo.py`,
  `_ThrottledSession`): усі виклики модуля йдуть через одну сесію, не частіше
  `KOMMO_MAX_RPS` запитів/сек (env, дефолт 2). Sleep — під локом, серіалізує
  старти запитів. Знизити без деплою можна через env `KOMMO_MAX_RPS`.
  **При відповіді 429/403** (rate limit / блок акаунта) інтервал між запитами
  автоматично росте ×2 до стелі `KOMMO_MAX_BACKOFF` сек (env, дефолт 5), а при
  успішних відповідях плавно спадає назад до базового. Тобто під тиском бот
  сам різко зменшує частоту й не «добиває» заблокований акаунт, а після
  відновлення повертається до норми — без ручного втручання і без заморозки
  воркера (макс. очікування на один запит = `KOMMO_MAX_BACKOFF`).
- **Короткочасний кеш `get_lead`** (`_lead_cache`, TTL `KOMMO_LEAD_CACHE_TTL`
  сек, дефолт 30; 0 = вимкнено): повторні фетчі того самого ліда в межах
  одного потоку (напр. `get_lead_details` викликає `get_lead`, а хендлер
  потім ще раз) беруться з кешу, а не з API. **Будь-який наш PATCH ліда
  (`update_lead_status`, `move_lead_to`) одразу інвалідовує запис**
  (`_invalidate_lead_cache`) — щоб loop-protection за тегом «Повернуто АІ» і
  самозцілення черги нерозібраних завжди бачили свіжий стан, а не старий.
  Дефолтні read-хендлери кешуються; критичні місця можуть викликати
  `get_lead(id, use_cache=False)`.
- `get_user_name` кешується безстроково (`_user_cache`).

⚠️ Якщо в лозі блокування Kommo бачиш запити з `?with=contacts`,
`?with=contacts,companies`, `/companies/{id}`, bulk `PATCH /api/v4/leads`
(без id) чи `GET /users?limit=250&with=group,role` — це **НЕ наш бот**
(він шле `?with=custom_fields`, PATCHить `/leads/{id}` поштучно, до
`/companies/` не звертається). Такий патерн — веб-UI/мобільний застосунок
Kommo (відкрита картка ліда, що автооновлюється) або інша інтеграція.

## Відомі підводні камені Kommo API

- **Формат вебхука нотаток (дзвінків) буває двох видів.** Kommo надсилає
  подію «Примечание добавлено» або пласко
  (`leads[note][i][note_type]`), або з вкладеним рівнем
  (`leads[note][i][note][note_type]`). Якщо парсити лише плаский —
  `_parse_notes` поверне порожньо, і весь розбір дзвінків (перший дотик,
  логування дзвінків РНК) тихо не працюватиме, хоча всі інші ланки
  (транскрибація, AI, Telegram) справні. `_parse_notes` тепер підтримує
  ОБИДВА формати (спершу вкладений, потім плаский). Діагностика —
  `GET /recent-webhooks`: дивись, чи ключі нотаток мають рівень `[note]`.
- `filter[contacts][0]` на `/api/v4/leads` — **не працює**, тихо
  ігнорується (повертає однаковий результат незалежно від contact_id).
  Альтернатива: `/api/v4/contacts/{id}?with=leads`.
- `filter[statuses][0][pipeline_id]` + `filter[statuses][0][status_id]`
  разом — працює коректно (перевірено живими запитами).
- Пагінація `/api/v4/leads` — ліди йдуть від найстаріших до найновіших;
  при великому обсязі за широкий діапазон дат однопрохідний запит з
  лімітом сторінок може не дійти до найновіших записів. Краще ділити
  широкий діапазон на менші під-запити.
- **DELETE не підтримується** для `/api/v4/leads` і `/api/v4/contacts`
  (405). Створені тестові ліди/контакти видаляти лише вручну в UI.
- **Не можна inline-створити контакт** разом зі створенням ліда — спершу
  `POST /api/v4/contacts`, потім лід з `_embedded.contacts:[{id}]`.
- `responsible_user_id` при `PATCH` угоди **не скидається**, якщо його не
  передавати (перевірено). А якщо передати `0` при створенні — Kommo все
  одно ставить власника токена (904923).
- `PATCH /api/v4/leads/{id}` з `_embedded.tags` **замінює** весь набір
  тегів. Щоб додати тег без втрати наявних — спершу GET, зібрати наявні за
  `id`, додати новий за `name` (див. `kommo.move_lead_to`).
- **Обов'язкові поля етапів** (`custom_fields[].required_statuses`): адмін
  їх ІГНОРУЄ при переміщенні, звичайні ролі — ні. Якщо угода не має
  заповнених обов'язкових полів цільового етапу, менеджер її туди не
  посуне (адмін — так). У воронці 8921932 обов'язкові: щоб зайти в 69693668
  — «Tип запиту» (2097965) + «Канал продажу» (2099549); у 69693672 —
  груз/звідки/куди; у 69716300 — багато полів приходу/розходу/авто.
- **Ролі з гранульованими `status_rights`**: усе, що не вписано явно —
  заборонено. Новий етап/воронка НЕ отримує прав автоматично. Записи для
  звичайних (не type=1) статусів вимагають поле `rights.export`; для
  Incoming (type=1) — навпаки, `export` не приймається.
- Створення етапу воронки: `POST /api/v4/leads/pipelines/{id}/statuses`
  (працює; `sort` Kommo може перерахувати).

## Відома пастка деплою (Render)

`scheduler.add_job(fn, ...)` МАЄ стояти після визначення `fn` у файлі —
інакше NameError на імпорті → gunicorn падає → Render мовчки лишає стару
версію (деплой «не котиться»). Якщо новий код не застосовується — перевір
`import app` локально (`python3 -c "import app"`), він ловить такі
forward-reference помилки, яких `py_compile` не бачить.
