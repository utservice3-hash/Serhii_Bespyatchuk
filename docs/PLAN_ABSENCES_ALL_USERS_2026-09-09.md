# План: відпустки й відсутності для БУДЬ-ЯКОГО акаунта дашборда

**Дата:** 09.09.2026 · **Статус:** план на затвердження, коду немає · **Гілка:** `feature/absences-all-users`
**Привід:** Дарʼя Протас (акаунт `utservice62`, адмін, «не з CRM») хоче поставити відпустку в
«Календарі команди», а її немає в переліку. **Питання Сергію надіслано:** дозволяти всім ролям?

## 0. Замір (прод, read-only, 09.09)
- `team_calendar_absences.manager_id` — `NOT NULL REFERENCES managers(id)`. Календар знає лише
  людей з CRM. **Без запису в `managers` — 4 активні акаунти:** Сергій (`utservice3`, opdir),
  Дарʼя Протас (`utservice62`, admin), бухгалтерія (`yuliauts`), рекрутер (`utsrecruiterr`, hr).
- Читачі таблиці: `routes/duty.ts` (календар, погодження, presence) і **`core/plans.ts`
  `presentWorkingDaysByManager`** — відсутності зменшують базис робочих днів плану менеджера.
- Імʼя ручного акаунта живе в `users.full_name` (додано для «не з CRM»), у CRM-акаунтів — у
  `managers.name`. Джойн у календарі сьогодні лише на `managers`.

## 1. Рішення
Відсутність привʼязується до **користувача**, а не до менеджера. Менеджерські відсутності
лишаються звʼязаними з `managers` через `users.manager_id`, тож плани нічого не втрачають.

### (а) Файли
| файл | стан | що |
|---|---|---|
| `db/schema.sql` | +міграція | `team_calendar_absences`: `manager_id` → NULLABLE; `+ user_id INTEGER REFERENCES users(id)`; `CHECK (manager_id IS NOT NULL OR user_id IS NOT NULL)`; бекфіл `user_id` з `users.manager_id`; індекс по `user_id` |
| `routes/duty.ts` | ~60 рядків | `calendarManagerScope` → перелік **акаунтів** (`users` LEFT JOIN `managers`): імʼя `COALESCE(m.name, u.full_name, u.email)`, команда з `managers`; `POST /absences` приймає `userId` (для CRM-людей виводить `manager_id` з `users.manager_id`); `queryAbsences` джойнить через `users`; `absenceScope`: менеджер — свої; тімлід — своя команда; безкомандні акаунти — бачить і погоджує **лише адмін-скоуп** |
| `core/plans.ts` | 0 рядків | читає `manager_id`, який для CRM-людей лишається заповненим — **не чіпаємо**, перевіряємо гейтом |
| `frontend/.../DutySection.tsx` | ~20 рядків | селект «Оберіть менеджера…» → «Оберіть співробітника…», значення `userId`; для акаунта без менеджера кнопка «на себе» |
| `frontend/src/api.ts` | +поле | `userId` у `createAbsence` |
| `auth/accessMatrix.ts` | 0 | роути ті самі, межі ті самі — звірити `#17` |
| `routes/duty.test.ts` | новий | гейти нижче |
| `testManifest.ts` | +записи | |

### (б) Дані
Міграція оборотна: `user_id` додається, `manager_id` лишається й заповнений у 100 % наявних
рядків. Бекфіл `user_id` — один `UPDATE … FROM users WHERE users.manager_id = a.manager_id`;
рядки, де в менеджера немає акаунта, лишаються з `user_id NULL` і працюють як раніше.
**Revert коду не відкочує колонку** — але вона нікому не заважає.

### (в) Чого НЕ робимо
- Не заводимо «фейкових менеджерів» для HR/бухгалтерії: це роздуло б ростери й таблицю з CRM.
- Не чіпаємо чергування (`duty_schedule`) — воно лишається лише для менеджерів РНК, це інша функція.
- Не міняємо правила погодження: тімлід не погоджує собі; безкомандних погоджує адмін.
- Не додаємо відпустки не-менеджерів у розрахунок планів — там немає плану, нема що зменшувати.

### (г) Що може зламатись — поіменно
- **`presentWorkingDaysByManager`** (плани): читає `manager_id`; після міграції для CRM-людей
  він заповнений, для нових акаунтів NULL і в `ANY($1)` не потрапляє. Гейт-дзеркало.
- **`/duty/presence`**: шукає за `manager_id` — та сама логіка, той самий гейт.
- Скоуп тімліда: безкомандні акаунти не мають `team_id`, тож у команду не потраплять; але
  тімлід-без-менеджера (якщо такий буде) побачить порожній календар — назвати словами.
- Імʼя: для акаунта без `full_name` покажеться email — правило фронту «невідоме словами».

### (д) Гейти
| # | твердження | червоніє, якщо |
|---|---|---|
| `#394` | акаунт без `managers` створює відсутність, вона повертається в календарі з імʼям із `full_name` | повернути `NOT NULL` або джойн лише на `managers` |
| `#394b` 🪞 | відсутність CRM-менеджера пише **обидва** ключі, і `presentWorkingDaysByManager` зменшує його робочі дні як раніше | загубити `manager_id` при записі |
| `#394c` | тімлід не бачить і не погоджує відсутність безкомандного акаунта; адмін — бачить і погоджує | розширити скоуп тімліда |
| `#394d` живий | після бекфілу `count(user_id IS NULL AND manager має акаунт) = 0` | бекфіл не відпрацював |

### (е) Приймання
Дарʼя Протас ставить собі відпустку → рядок у календарі з її імʼям, статус «на погодженні» →
Сергій погоджує. Паралельно: сума робочих днів плану по будь-якому менеджеру з approved-
відпусткою у вересні **не змінилась** (одним запитом до і після). Скріншот дня в календарі.

### (ж) Обсяг
Схема + роут + гейти: 1 сесія. Фронт + приймання: 1 сесія. Разом 2 сесії, один викат.
