# Роути, чиєю єдиною межею є scope-кламп (борг кроку B)

**Знято 31.07.2026** після інциденту з HR: роль отримала `data_scope='company'`, і три
оглядові ендпоінти, які трималися ЛИШЕ на `if (auth.role === "manager") return 403`,
відкрилися ролі, у якої немає ні `overview`, ні `loyalty`, ні `manager-report`.

Три симптоми закрито (додано в `ROUTE_TAB`). Цей файл — про **хворобу**:
у `rbac.ts` стояло припущення «решта `/api/dashboard/*` — без tab-гейта, scope все одно
клампить». Для company-ролі клампа **немає за визначенням**, тож припущення хибне.
Наступна роль зі `scope=company` відкриє ці роути так само тихо.

## Що з цим робити (крок B)

1. **Не закривати по одному після інциденту.** Пройти список цілком, для кожного
   вирішити: `ROUTE_TAB` / `requirePerm` / свідомо публічний.
2. **Дефолт має стати протилежним:** роут без явної межі — помилка конфігурації, а не
   «оглядові дані». Тобто потрібен тест, який вимагає, щоб КОЖЕН роут мав або запис у
   `ROUTE_TAB`, або perm-гейт, або рядок у списку свідомих винятків (як
   `ACCEPTED_DIVERGENCES` для ролей).
3. **Зліпок покриває 65 із 173** — розширити до всіх, інакше «матриця зелена» означає
   лише «зелена там, куди ми подивились».

## Суміжний борг — зліпок СКОУПУ, а не лише статус-кодів

Матриця міряє **коди відповідей**. Зміна scope HR не зрушила б жодної клітинки, якби
роль уже мала 200 і просто побачила більше рядків. Тобто розширення обсягу даних
матриця **не ловить**.

Ідея (схвалена власником 31.07.2026): знімати не числа (вони пливуть від даних), а
**відношення-інваріанти**, які переживають зміну даних:

- менеджер бачить **строгу підмножину** того, що бачить його тімлід;
- тімлід — підмножину того, що бачить адмін;
- роль **без екрана** не бачить із нього **жодного** рядка;
- сума по ролях не перевищує загальну (немає «вигаданих» рядків).
