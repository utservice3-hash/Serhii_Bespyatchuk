# Бекапи та аварійне відновлення — UTS Dashboard

Документ описує, **де живуть дані**, **як вони бекапляться** і **що робити, якщо дані втрачено**. Тримати актуальним.

## 1. Де живуть дані

| Компонент | Де | Що там |
|---|---|---|
| **База даних** | **Neon** (managed Postgres, `…aws.neon.tech`, база `neondb`) | Уся аналітика: угоди, менеджери, задачі, плани, дебіторка, події етапів тощо (21 таблиця) |

## 2. Два рівні бекапів

### Рівень 1 (основний) — Neon PITR
Neon **автоматично** тримає історію змін і дозволяє **Point-in-Time Recovery** — відновити стан БД на будь-яку секунду в межах retention.
- Консоль: **console.neon.tech** → проєкт → **Branches / Restore**.
- **Перевірити/збільшити retention** (на безкоштовному тарифі — зазвичай 1 день; варто підняти до 7–30 днів; це кілька $/міс і воно того варте).
- Дає ще й **branching**: миттєва копія БД для тестів, не чіпаючи прод.

### Рівень 2 (незалежний) — локальні CSV-бекапи
Щоночі о **03:00** job `backupDb` вивантажує **кожну таблицю** в gzip-CSV на наш сервер:
```
/home/evraziat/uts.ua/dashboard/backups/uts_YYYY-MM-DD_HH-MM-SS/
    ├── deals.csv.gz, managers.csv.gz, … (21 файл)
    └── MANIFEST.txt
```
- Ретенція **14 останніх** бекапів (старі авто-видаляються).
- Формат — нативний Postgres `COPY … CSV HEADER`, тож **відновлюється в будь-який Postgres**.
- Ручний запуск будь-коли: `cd backend && npm run backup`.
- **Навіщо, якщо є Neon?** На випадок втрати самого Neon-акаунта/проєкту — це копія **поза Neon**, під нашим контролем.

> 🔒 **Рекомендація:** раз на тиждень качати найсвіжішу теку `backups/uts_*` собі (Google Drive / інший сервер), щоб копія була ще й **поза сервером evraziat**. Ідеал «3-2-1»: 3 копії, 2 носії, 1 поза-майданчик.

## 3. Сценарії втрати даних — що робити

### Сценарій A. Зіпсували/видалили частину даних (кілька угод, одна таблиця)
Найшвидше — **Neon PITR або branch на момент ДО інциденту**:
1. console.neon.tech → проєкт → **Restore / Branches**.
2. Створити branch на timestamp **до** помилки → перевірити дані на ньому.
3. Або зробити повний restore проєкту на цей момент (обережно — відкотить усе).
4. Якщо треба лише кілька рядків — підняти branch, зчитати потрібні рядки й вручну повернути в прод.

### Сценарій B. БД недоступна / пошкоджена, Neon живий
1. Перевірити стан у console.neon.tech (compute suspended? — Neon сам будить).
2. `curl https://dashboard.uts.ua/api/health` — покаже стан синку.
3. Якщо БД ок, але дані «застигли» — глянути `sync_state.last_error`; перезапустити бекенд (див. `CLAUDE.md` → Деплой).

### Сценарій C. Повна втрата (Neon-проєкт зник / мігруємо на новий Postgres)
1. **Підняти новий Postgres** (новий Neon-проєкт, або будь-який Postgres).
2. Прописати новий `DATABASE_URL` у `backend/.env`.
3. **Створити структуру:** `cd backend && npm run migrate` (застосує `schema.sql` + мапінг етапів).
4. **Залити дані** з останнього локального бекапа (нижче).
5. Запустити бекенд — синк із Kommo підтягне свіже й «догляне» угоди.

## 4. Як відновити дані з локального CSV-бекапа

Кожен файл — це `COPY … CSV HEADER`. Відновлення (порядок таблиць важливий через FK; спершер `teams`, `managers`, `users`, потім решта):

**Варіант 1 — через `psql` (з машини, де він є):**
```bash
gunzip -k backups/uts_.../teams.csv.gz
psql "$DATABASE_URL" -c "\copy teams FROM 'teams.csv' WITH (FORMAT csv, HEADER)"
# повторити для кожної таблиці у правильному порядку
```

**Варіант 2 — без psql (є лише Node на сервері):**
Я підготую скрипт `npm run restore -- <тека_бекапа>` (COPY FROM через `pg-copy-streams`), який заллє всі таблиці в правильному порядку. **Скажи — додам його** (не тримаю його ввімкненим, щоб випадково не перезаписати прод).

> Порядок таблиць для відновлення: `teams → managers → users → deals → pipeline_stage_map → deal_stage_events → lead_transfer_events → plans → funnel_plans → tasks → receivables → receivable_notes → monthly_carryover → monthly_carryover_mgr → app_settings → messages → feedback → ai_messages → news → …`

## 5. Регламент (щоб бекапи реально працювали)

- [ ] **Щотижня:** глянути, що в `backups/` зʼявляються свіжі теки (job живий). Скачати найсвіжішу поза-сервер.
- [ ] **Раз/місяць:** перевірити retention у Neon (console) — має бути ≥ 7 днів.
- [ ] **Раз/квартал:** **тест-відновлення** — підняти порожній Postgres, залити бекап, переконатись, що дашборд стартує. Бекап без перевірки відновлення — це не бекап.
- [ ] **Моніторинг:** підключити UptimeRobot на `https://dashboard.uts.ua/api/health` (алерт, якщо `ok!=true` або синк `stale`).
