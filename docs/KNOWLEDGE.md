### "Передачі" (Google Sheets) — ще не підключено

Метрика "Передані прорахунки від лідогенератора" **не повинна** рахуватись
прямим підрахунком лідів у Kommo зі статусом `69716164` за період — там є
технічні дублікати/повторні заходи. Формула:

> COUNT(рядків листа "Передачі") за обраний період, групування за
> `transferred_at`.

Бот, що пише в лист, вже відфільтровує дублікати й технічні повторні
заходи (статуси-винятки вище) — рядок листа = валідна передача.

**Блокери для реалізації** (ще не надано користувачем):
1. ID Google-таблиці
2. Метод доступу (service account / публічне посилання / існуючі
   креденшали бота)
3. Точні назви колонок у листі "Передачі", включно з колонкою, що
   визначає менеджера-отримувача

Метрика "к-сть відправлених авто" — рахується напряму з Kommo:
угоди в `pipeline_id = 8921932`, `status_id = 69716300` ("АВТО ПРАЦЮЄ"),
за період.

## Команди / Менеджери

- `syncManagers()` (`backend/src/jobs/syncKommo.ts`) синхронізує команди й
  менеджерів з Kommo `groups`/`roles`.
- **Тім-лід визначається за підстрокою `"тимл"`** (не `"тимлід"`!) —
  Kommo використовує російське написання ролі `"Тимлид"` (и, а не і).
  Перевірка `role.toLowerCase().includes("тимл")` покриває обидва варіанти
  написання.
- Адмін без явно вибраної команди автоматично бачить дані першої команди
  зі списку (`teams[0]`) — фронтенд (`Dashboard.tsx`) не вимагає ручного
  вибору команди для показу даних.
- 3 легасі-команди (РНК id=1, РПК id=2, Лідогенератори id=3) з нульовою
  кількістю менеджерів і `kommo_group_id = NULL` були видалені як
  осиротілі (перевірено: 0 references у `users`/`managers`).

## Постійні клієнти (loyalty KPI)

Бізнес-правила (підтверджені користувачем):

- **"Постійний" клієнт** — 3+ замовлення за поточні останні 3 місяці
  (rolling window, не календарний квартал).
- **"At risk"** — ТІЛЬКИ ті, хто був постійним (3+) у *попередньому*
  3-місячному вікні, а тепер випав нижче порогу. Не будь-який клієнт
  з < 3 замовлень.
- **"Замовлення"** = угода, що дійшла до `funnel_stage = 'paid'`
  (статус 69716460 "Оплата отримана" АБО 142 "Успішна угода" в
  pipeline_id 8921932).
- **Ідентифікація клієнта** — за назвою, з нормалізацією: "Смартекс" і
  "ТОВ Смартекс" — один і той самий клієнт. Реалізовано через
  `client_key` (нормалізована назва: lowercase, без пунктуації, без
  токенів ТОВ/ФОП/ПП/ООО/ЗАТ/ТЗОВ/ПРАТ та фраз
  "товариство з обмеженою відповідальністю" / "общество с ограниченной
  ответственностью") — `backend/src/utils/clientName.ts`.
- `deals.name` **не надійний** для ідентифікації клієнта — у вибірці
  зустрічаються маршрути ("Запоріжжя – Київ"), телефони, плейсхолдери
  ("Lead #61562535"), а не лише назви компаній. Реальна назва клієнта
  береться з Kommo `companies`/`contacts` (через окремі bulk-запити
  `/api/v4/companies`, `/api/v4/contacts` — embed `with=contacts,companies`
  на `/api/v4/leads` дає лише ID, без назв).
- Реалізація: `GET /dashboard/loyalty` (`backend/src/routes/dashboard.ts`),
  фронтенд-таб "Постійні клієнти" (`frontend/src/pages/Dashboard.tsx`).
- **Відомий пробіл**: інкрементальна синхронізація заповнює
  `client_name`/`client_key` лише для угод, що змінювались після
  останнього sync. Існуючі історичні угоди (~76k рядків) потребують
  одноразового повного backfill-синку (повторний `fetchAllDeals` без
  `updatedAfter`, тобто `windowStart = 0`/відсутній), щоб отримати
  `client_name`/`client_key` retroactively. Це ще не виконано.

## Деплой (production)

Деплой виконується через HTTP relay (`relay-*.php`, заголовок
`X-Relay-Token`, POST-поле `cmd`, виконується в cwd
`/home/evraziat/uts.ua/dashboard`):

1. `git pull`
2. `npm run build` (backend: tsc; frontend: tsc+vite)
3. Для фронтенду: `cp -r dist/* ../` — копіювання в web root
4. `pkill -f 'node.*dashboard/backend'` — supervisor автоматично
   перезапускає backend
5. Перевірка через `/api/health`

Токен релею не зберігається в репозиторії (передається користувачем
у чаті за потреби) — деплой на прод виконується за окремим запитом
користувача, а не автоматично при кожному коміті.
