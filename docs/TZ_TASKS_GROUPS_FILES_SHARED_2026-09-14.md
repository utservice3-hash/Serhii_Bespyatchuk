## 2. Що робимо

### 2.1 Групи задач
- Нова таблиця `task_groups` (id, name, owner_id → users, parent_id для вкладеності на майбутнє, created_at). Колонка `tasks.group_id` NULL-able.
- Група **особиста**: належить акаунту-власнику, створювати може будь-хто, чужі групи не показуються. Задача в чужій групі для іншого глядача виглядає як «без групи». **Група не змінює доступ**, лише розкладку.
- Екран: ліва панель «Групи» над списком, «Без групи» за замовчуванням, перетягування не робимо, вибір групи у формі й у рядку.
- Поле «команда» лишається як є: це інший вимір (чия команда), а не папка.

### 2.2 Файли до задачі
- Нова таблиця `task_files` за зразком `doc_files`: task_id, name, stored_name, mime, size_bytes, created_by, created_at. Тека `backend/task-files` поруч із `documents`, поза публічним `/api/files`.
- `POST /tasks/:id/files` (multipart), `GET /tasks/:id/files`, `GET /tasks/:id/files/:fid` (віддача з перевіркою доступу до задачі), `DELETE` лише автору файла або адміну.
- Ліміт **5 МБ** на файл (рішення Романа 14.09), до 10 файлів на задачу. Зображення й PDF відкриваються в браузері, решта на завантаження.
- 🔴 Заміряти до початку: скільки місця на диску хоста і чи `documents` справді потрапляє в бекап (у коментарі так написано, перевірити скриптом бекапу).

### 2.3 Спільна задача
- **Правило видимості:** автор бачить задачу, яку призначив, завжди, незалежно від ролі. Зміна в `routes/tasks.ts:59`: до умов менеджера й тімліда додати `OR t.created_by = <я>` для призначених задач (зараз це є лише для особистих без виконавця).
- **Стрічка доповнень:** таблиця `task_comments` (task_id, author_id, body, created_at). Поле `tasks.comments` лишається як «короткий коментар» у рядку, стрічка з'являється в розкритті задачі. Писати можуть автор, виконавець, тімлід виконавця й адмін.
- **Історія статусу:** `task_status_log` (task_id, from, to, changed_by, at). Автор бачить, хто й коли рухав статус.
- **Сповіщення:** **відкладено** (рішення Романа 14.09: спершу зʼясувати, чи є робочий Telegram-бот). У цьому проході лише бейдж «є нове» у задачнику для автора й виконавця. Канал додається окремим кроком.
- Виконавцем може бути **будь-який акаунт**: `tasks.assignee_user_id → users` поруч зі старим `assignee_id`, старе поле не чіпаємо (Звіт читає його). Виводиться одне імʼя.

## 3. Чого не робимо
1. Не чіпаємо KPI-парасольки, `metrics_json`, `plan`, `daily_kpi`, реактиваційні задачі, 1×1.
2. Не робимо вкладені групи в інтерфейсі (поле `parent_id` є, екран плоский).
3. Не робимо перетягування між групами.
4. Не видаляємо файли фізично при видаленні задачі одразу: помічаємо, чистимо нічною джобою через 30 днів.
5. Не переносимо старе поле `comments` у стрічку автоматично.

## 4. Що може зламатись — поіменно
- `/report-plan` і картка менеджера читають `tasks` (замок `#56`). Додаємо колонки, не міняємо наявні → гейт має лишитись зеленим, це перевіряється прогоном.
- `GET /tasks` для менеджера почне повертати більше рядків (призначені ним). Перевірити, що особисті чужі задачі й далі приватні (`#` на протікання є в тестах роуту).
- Матриця доступу: три нові роути файлів і два для коментарів → рядки в `accessMatrix.ts`, інакше `#17` червоніє.

## 9. ЩО ЗАМІР ЗМІНИВ ПРОТИ ЦЬОГО ТЗ (реалізація 14.09.2026)

ТЗ складався по коду, і два його твердження замір **опроверг**. Записано тут, бо
документ, який пережив свою неправду, гірший за відсутній.

### 9.1 🔴 «`documents` потрапляє в нічний бекап» — НЕПРАВДА
ТЗ (§2.2) переказав це з коментаря в `routes/documents.ts:12`. Заміряно 14.09:
`jobs/backupDb.ts` бере **всі таблиці** з `pg_tables` (у бекапі за 14.09 — 90 із 90,
`MANIFEST.txt` це підтверджує), а файлових тек не бере **жодна** джоба й **жоден**
крон: у теці бекапу нуль згадок `documents`, `uploads` і `tar`; у коді нуль
`tar`/`rsync`/`cpSync`. Тобто **рядок `task_files` у бекапі буде, а БАЙТИ файла — ні.**

**Наслідок, прийнятий свідомо:** видалення вкладення зроблено **мʼяким**
(`deleted_at`, байти лишаються), а віддача відсутнього файла відповідає «файл
відсутній на диску», а не порожнім 200. Хибний коментар у `documents.ts` виправлено.
**Борг:** бекапу файлових тек немає — окреме рішення власника (додати `tar` у джобу
чи прийняти ризик).

### 9.2 🔴 «Автор не бачить призначену задачу» — ЛИШЕ ДЛЯ РОЛІ МЕНЕДЖЕРА
ТЗ (§1) подав це як загальну прогалину. Насправді в SQL видачі `t.created_by = me`
**уже стояв** у гілках тімліда й наскрізного; бракувало його рівно в гілці менеджера,
і лише там (`t.assignee_id IS NULL AND t.created_by = …` — тобто для задач БЕЗ
виконавця). Отже зміна поведінки вужча, ніж обіцяв ТЗ: **автор-МЕНЕДЖЕР** тепер
бачить задачу, яку поставив колезі. Для інших ролей видача не зрушила.

### 9.3 Додано понад ТЗ — і чому без цього не працює
| що | чому |
|---|---|
| таблиця `task_views` (5-та, у ТЗ було 4) | бейдж «є нове» означає «зʼявилось після мого останнього перегляду». Без збереженого моменту перегляду це твердження — здогад |
| роут `GET /tasks/assignees` | селект «виконавець-акаунт» нічим наповнити: жоден наявний роут не віддає список акаунтів тому, хто не адмін. Віддає `id` + імʼя, **без email** |
| `groupId` дозволено субʼєкту задачі з 1×1 | група особиста й доступу не змінює, ведучий бачить задачу незалежно від папки. Заборона означала б «розклади свої 1×1 задачі по папках — 403» |
| видалення ЗАДАЧІ знімає байти вкладень | `task_files.task_id` має ON DELETE CASCADE: разом із задачею зникає єдиний запис про те, який файл на диску їй належав. Без цього байти — сироти назавжди |
| нові таблиці в `FORBIDDEN_TABLES` і REVOKE | `GRANT SELECT ON ALL TABLES` накриває кожну нову таблицю: заборона на `tasks` без заборони на `task_comments` ховала заголовок і віддавала розмову |

### 9.4 Чесна межа історії статусу
`tasks.status` пишуть ще **шість** місць поза карткою (оцінювач KPI, реактивація,
1×1, звіт) — вони в лог НЕ пишуть. Тому під історією на екрані стоїть підпис
«рухи через інтерфейс» і окремий рядок «автоматичні зміни тут не показуються»:
без нього порожній лог читався б як «ніхто не рухав» там, де рухала джоба.
