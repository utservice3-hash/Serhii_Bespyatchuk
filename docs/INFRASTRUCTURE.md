## 1. Принцип: custom-логіка — своя, «загальне» — готове

## 2. Metabase — ad-hoc аналітика (рекомендую)

**Що дає:** керівник/аналітик відкриває веб, кликами будує таблиці/графіки/дашборди по будь-яких полях, зберігає, шарить. Без звернень до розробника.

**Як підняти (≈1 год):**
1. Розгорнути Metabase (Docker: `metabase/metabase`, або хмара metabase.com).
2. Підключити **той самий Neon Postgres** — але **окремим read-only користувачем** (щоб аналітики не могли нічого змінити):
   ```sql
   CREATE ROLE metabase_ro LOGIN PASSWORD '…';
   GRANT CONNECT ON DATABASE neondb TO metabase_ro;
   GRANT USAGE ON SCHEMA public TO metabase_ro;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO metabase_ro;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO metabase_ro;
   ```
3. Готово — таблиці видно, будуються звіти.

**Межа:** Metabase бачить **сирі таблиці**, не наші «розумні» метрики (мінус-угоди, знімки оплат). Для складних правил — лишається наш дашборд. Metabase = «покопатись у даних», наш застосунок = «правильні бізнес-показники».

## 6b. Зʼєднання з БД: ПРЯМЕ, не через пулер Neon (рішення власника 05.08.2026)

`DATABASE_URL` вказує на **прямий** ендпоінт Neon, не на `-pooler`. Це свідомо, і
ось чому — щоб через півроку ніхто не «оптимізував» перехід:

- наш **read-only запобіжник** тестового харнесу стоїть на `PGOPTIONS=-c
  role=test_readonly`, який їде у **стартовому пакеті зʼєднання**. Пулер Neon
  працює в **transaction mode**, де сесійні опції не гарантовані — тобто
  запобіжник, що вже одного разу врятував прод від справжнього `DELETE`, став би
  «спрацьовує через раз, а виглядає завжди зеленим»;
- економити нема чого: `max_connections = 901`, пул застосунку **15**, реально в
  роботі одиниці зʼєднань (заміряно 05.08.2026).

🔴 Перехід на pooled-ендпоінт можливий ЛИШЕ разом із заміною механізму read-only
(наприклад, окремим користувачем БД замість ролі в опціях) — і це окреме рішення,
а не деталь конфігурації.

**Пул застосунку `max: 15`** (`db/pool.ts`). Був 6; `/overview` робить 35 запитів
на один запит екрана, тож четверо одночасних користувачів ставили 140 запитів у
чергу на 6 зʼєднань. Заміряно до/після: `/overview` ×4 8 546→4 550 мс, ×8
8 627→4 331 мс.

## 6f. 🔒 ЗАМОК ПРОД-ЧЕКАУТУ (з 26.08.2026)

```
npm run lock -- --status [--log]
npm run lock -- --take    --who=<чат> --reason="що саме робиш"
npm run lock -- --release --who=<чат>
npm run lock -- --steal   --who=<чат> --reason="чому забираєш"
```

🔴 **ЧОГО ВІН НЕ РОБИТЬ, І ЦЕ СКАЗАНО ПЕРШИМ.** Замок **не унеможливлює** зіткнення —
будь-хто може виконати `git merge` руками, не спитавши нікого. Він **робить зіткнення
видимим і дорогим**: «я не знав, що там хтось є» перестає бути правдою, а перехоплення
лишає імʼя. Обіцяти більше означало б продати мʼютекс, якого тут немає.

🔴 **БЕРЕТЬСЯ ЗА ДОТИК ДО ЧЕКАУТУ, А НЕ ЗА НАМІР ДЕПЛОЮ.** Намір — стан голови; дотик —
те, що ламає чуже дерево. 26.08.2026 мій `merge --ff-only` не пройшов, а окремі виклики
збірки й копії — пройшли, і в докрут поїхав бандл чужого коміту. Тобто «я ж не деплою,
я лише подивлюсь» і є той випадок, заради якого замок існує.

**Два файли, і поділ не косметичний:**

| файл | що це | доля |
|---|---|---|
| `.deploy-lock` | **претензія**; її існування і є замок | зникає при звільненні |
| `.deploy-lock.log` | **журнал**, append-only | НІКОЛИ не видаляється |

Тому «хто тримав» — не поле, яке можна переписати, а історія, яку можна лише дописати.
Обидва в `.gitignore`: це локальний стан, не код.

### ⏳ TTL 20 хв НЕ ЗВІЛЬНЯЄ САМ

Протермінування рахується **на читанні** і **нічого не звільняє**. Автозвільнення за
таймером — це та сама крадіжка, тільки **без імені й без причини**: замок зникає, а в
журналі порожньо. Прострочений замок лишається ЗАЙНЯТИМ; забрати його можна лише явно:

```
npm run lock -- --take --who=<ти> --after-ttl
```

Причину такої події складає **інструмент**, а не перехоплювач: вона називає попереднього
тримача, вік замка й те, що він робив. `--steal` існує окремо — для аварії, коли TTL ще
не вийшов, — і **вимагає причини руками**.

### 🔓 «Чекаут вільний» ≠ «замка немає»

Вільний чекаут — це **немає змінених ВІДСТЕЖУВАНИХ файлів** (`git status --porcelain`
без `??`). Докрут живе в корені репозиторію, тож нетрековані файли там є **завжди** —
критерій «робоче дерево чисте» тут не працює в принципі.

### ❓ Чому не визначати зайнятість автоматично

Питання законне: чому не дивитись на `git status`, свіжий `dist` чи `app_boot`. Бо
**тиша має щонайменше три причини, і вони вимагають протилежних дій**:

| що видно | могло означати | правильна дія |
|---|---|---|
| чекаут чистий, нічого не рухається | ніхто не працює | заходь |
| те саме | пауза **посеред** чужого викату | не чіпай |
| те саме | чужий викат обірвався й лишив мішаний стан | розберись, потім чіпай |

**Відсутність сигналу — це не стан.** Автовизначення обрало б перший рядок і мовчки
помилялось би у двох випадках із трьох; замок вимагає, щоб про свій намір сказали
словами. Саме на цьому 26.08.2026 я вже спробував побудувати поллер «тиша = вільно» —
і та «тиша» була б паузою перед чужим аварійним викатом.

### 🧩 Скрипт бере замок сам, ручний дотик — ні

`deploy:check` має крок `lockTake` — **другим, ще до `standTo` й до будь-якого дотику
до дерева**; `deploy:run` має `lockRelease` — рівно за `accept`.
🔧 **Виправлено 03.09.2026 (відставання від коду).** Тут стояло «`deploy:run` має кроки
`lockTake` (перед `ff`)». Крок переїхав у фазу `check`, і це не косметика: за старим
текстом замок брали б ПІСЛЯ того, як стенд уже переставлено. Перевірка — `--dry-run`.
При **аварійному** виході замок лишається взятим **навмисно** — недороблений викат і є
той стан, заради якого замок існує; вихід каже про це вголос і дає команду звільнення,
щоб замок не читався як забуте сміття.

### 🧭 `standTo` — стенд ставить ЛАНЦЮГ, а не скрипт у `/tmp`

🔧 **Додано 03.09.2026: цього кроку у файлі не було жодного разу (нуль згадок).**

`standTo` — **третій** крок фази `check`, одразу за `lockTake`: він ставить стенд на

Крок **відмовляється** працювати й називає причину, якщо: `--target` не заданий · sha
не існує · дерево брудне. Відмова, яка не називає власного виходу, коштує наступному
годин — тому вона тут іменна.

⚠️ **Bootstrap, який видно лише один раз.** Ланцюг виконується з `dist`, а `dist`
збирається кроком `buildBack` **пізніше**. Отже поки `standTo` не викочений, у плані
його ще немає — і стенд на першу ціль доводиться ставити руками:
`git -C <стенд> checkout --detach <sha>`. Після першого викату це зникає.

### 🧪 `acceptMatrix` — і його ТРЕТІЙ стан «НЕ ВИМІРЯНО»

🔧 **Додано 03.09.2026: крок не згадувався у файлі жодного разу (нуль згадок).**

Останній змістовний крок фази `run`, **після `lockRelease`**. Ганяє повний зліпок
доступу (`#11`) проти живого прода.

**Чому після звільнення замка.** Замок стереже **чекаут**, а ця проба ходить по HTTP і
чекаута не торкається; тримати чужу чергу зайві ~4 хвилини заради того, чого замок не
захищає, — не та ціна.

🔴 **Але в цієї ціни є друга половина, і вона названа не одразу:** щойно замок віддано,
наступний бере його й за кілька хвилин **перезапускає прод — просто під твоєю пробою**.
Спостережено 03.09.2026: замок віддано о 12:55, узято іншим о 12:55:35.

Тому крок має **три** стани, а не два:

| вирок | коли |
|---|---|
| ✅ зелено | проба пройшла |
| 🔴 червоно | дрейф зліпка на **незмінному** коді — розійшлись зліпок і прод |
| ﹣ **НЕ ВИМІРЯНО** | `health.version` **змінився** між початком і кінцем проби |

**«Не виміряно» — це не зелене.** Воно означає рівно те, що написано: матрична проба
по цьому викату **не зроблена**, і дрейф доступу лишається невідомим; прогнати
`npm run test:matrix` окремо, на тихому проді.

⚠️ **Межа, без якої третій стан став би лазівкою:** зелене **ніколи** не стає «не
виміряним». Інакше ланцюг дістав би спосіб не міряти взагалі, оголошуючи будь-яке
червоне незміряним.

Підстава ширша за цей крок і вже діяла в нас в інших місцях: **5xx і зміна стану
означають «не виміряно», ніколи «порушено»**. Хибна тривога в детекторі ДОСТУПУ дорожча
за пропуск — вона відправляє людину звіряти клітинки рішенням власника.

## 6h. 🔤 СМУГА І РЕЖИМ — РІЗНІ ОСІ, І СПІЛЬНИХ СЛІВ У НИХ НЕМАЄ (27.08.2026)

**Смуга** — про **дисципліну проходу**: що зробити, ПЕРШ НІЖ чіпати прод.
Значення: **косметична** · **повна**.

**Режим** — про **кроки ланцюга викату**: `--mode=light` · `--mode=full`.
Визначається тим самим дифом, але **іншим правилом**.

🔴 **`--mode=light` ВУЖЧИЙ, НІЖ «легкий прохід».** Він вимагає, щоб диф був **лише у
`frontend/`** (крок `lightAdmission`), і відмовляє на будь-якому файлі поза ним.
«Бекенд без фронту й без схеми» — це **`--mode=full`**, хоч на слух і звучить легшим.

🔴 **СМУГА Й РЕЖИМ РОЗХОДЯТЬСЯ В ОДИН КОНКРЕТНИЙ БІК.** Косметична смуга завжди дає
`--mode=light`. Але **`--mode=light` НЕ означає косметичної смуги**: диф може бути лише
у `frontend/` і при цьому міняти підпис ПОРУЧ ІЗ ЧИСЛОМ — а це **повна смуга**, із
заміром, планом і саботажами. Режим каже, ЯКІ КРОКИ виконати; смуга каже, ЩО ЗРОБИТИ
ДО того, як їх запускати. **Зелений `lightAdmission` не є дозволом пропустити план.**

⚠️ **Слово «легкий» до смуги не вживається.** 27.08.2026 прохід дістав вказівку
«режим легкий» у сенсі «фронт не чіпаємо», спробував `--mode=light` і отримав СТОП на
`lightAdmission` із десятьма файлами поза `frontend/`. Інструмент мав рацію; помилкою
було одне слово у двох значеннях.

| що сказали | що це означає в коді |
|---|---|
| «фронт і схема не чіпаються» | `--mode=full` |
| «косметика, лише стилі й геометрія фронту» | `--mode=light` |
| «повна смуга» | про замір/план/саботажі, **не** про `--mode` |
| «`lightAdmission` зелений» | лише про кроки; **смугу він не знижує** |

## 7. Процедура деплою в прод (порядок кроків)

🚀 **З 25.08.2026 цей ритуал ЗАПИСАНО СКРИПТОМ** — `npm run deploy:check` (у контейнері)
і `npm run deploy:run` (на проді). Реєстр кроків із причинами — `src/tools/deployPlan.ts`;
перелік нижче лишається чинним і потрібен, коли скрипт недоступний.

🔴 **`deploy:check` — ЛИШЕ В КОНТЕЙНЕРІ.** На проді він відмовляється стартувати (код 3):
фаза робить `rm -rf dist && npm run build`, тож у прод-чекауті перезбере `dist` ПРОДА з
тієї гілки, що там лежить. 26.08.2026 так уже зробили з чужої незапушеної гілки — прод
лишився на старому sha, а на диску опинився бандл іншого коду.

🔗 **Фази стикуються без ручного кроку:** `deploy:run --target=<sha>` бере ціль ЯВНО.
Звіряти артефакт із HEAD прод-чекауту не можна — до `ff` там стоїть старий sha, і збігу
не було б ніколи. Sha беруть із поля `branchSha` артефакта, що лишає `deploy:check`.

⚠️ **Скрипт НЕ деплоїть сам** і НЕ прибирає жодного кроку: він робить непотрібною
памʼять про них. Режим вимагається явно (`--mode=full|light`), мовчазного дефолту немає.
`deploy:run` не стартує без свіжого артефакту від `deploy:check` — і свіжість звіряється
за ДВОМА sha (гілки і прода), бо перевірка тригодинної давності могла звірятись із продом,
що відтоді зрушив вісім разів.

📐 **Навіщо, числом:** за одну добу 25.08.2026 один виконавець зробив чотири викати — і
шість кроків виконав по-різному; `npx tsc -b` фронту не виконувався ЖОДНОГО разу з чотирьох.

Виносячи збірку, ми **розширюємо вікно між заміром бази й доставкою з ~1 хв до ~21 хв**.

1. `git fetch` у стенді (без нього `merge-base` бреше проти застарілого tracking-ref);
2. `health.version` У ЦЮ МИТЬ — предок HEAD стенда;
3. **`dist/version.json` == HEAD стенда.** Перші два — про дерево, а доставляємо ми `dist`:

заново. **Ціна перезбору заміряна: ≈169 с** (BE 4.5 + FE 11.5 + `npm test` 75 + базовий
прогін 78). Очікувана ціна винесення — `0.25 × 2.8 хв ≈ 45 с` на викат проти ~19.5 хв
звільненого чекауту.

🔴 **НЕ «швидко домержити під замком»** — це поверне збірку в чекаут, тобто скасує весь сенс.

   🔴 **ПОПЕРЕДНЯ РЕДАКЦІЯ КАЗАЛА «pid не видно взагалі» — ЦЕ ВІРНО ЛИШЕ ДЛЯ SSH.**
   Суперечність назвали ДВА чати незалежно, і ціна помилки не косметична: читач
   ішов писати в підтримку замість рестарту за 8 секунд.

   | канал | `ps -C node` | `ps -eo args` | `kill -TERM` |
   |---|---|---|---|
   | SSH | порожній | процесу не видно (інший namespace) | ❌ нема кого вбивати |
   | **relay** | **порожній теж** | ✅ **видно** `node dist/index.js` | ✅ **працює** |

   Тобто `ps -C node` порожній в ОБОХ каналах — саме він і створив враження, що pid
   не існує. Через relay процес видно повним переліком аргументів.

   **Робочий спосіб — ОДНІЄЮ командою** (pid не має протухнути між викликами):
   ```
   PID=$(ps -eo pid,args | awk '$2=="node" && $3=="dist/index.js" {print $1}' | head -1)
   [ -n "$PID" ] && kill -TERM "$PID" || echo "процес не знайдено — НЕ вбиваю нічого"
   ```
   ⚠️ **ТА САМА ПАСТКА КУСАЄ Й ПРИ ПЕРЕВІРЦІ «ЧИ ЩЕ БІЖИТЬ»** (спіймано 27.08.2026):

   скінчився, — він знайшов сам себе. Питати треба так, щоб відповідь не містила
   питання: `ps -eo etimes,args | grep "node --test" | grep -v grep`, або звірятись за
   pid, або за ознакою завершення в самому лозі. Це той самий клас, що «наявність
   артефакту ≠ його придатність»: інструмент бадьоро відповідає про роботу, якої немає.

   🔴 **НЕ `pgrep -f node`**: `-f` матчить ВЛАСНИЙ командний рядок виклику, тож

   ### 🔁 Що відбувається після `exit 1` (замір 25.08.2026)

   Питання стояло відкритим: `loadRolesOrDie()` → `exit 1` має сенс лише якщо процес
   хтось підніме. Тепер відповідь спирається на замір, а не на здогад.

   **Ланцюг нагляду на проді** (прочитано `ps`, read-only):
   ```
   lve_suwrapper (ppid 1)
     └─ bash -c 'source ~/.bashrc; cd …/backend && npm start 2>&1 | tee -a <log>'
         └─ npm start └─ node dist/index.js
   ```

   **① КОД ВИХОДУ НЕ ДОЇЖДЖАЄ НІКУДИ — заміряно в контейнері на тій самій формі:**

   | що зробив node | код `bash -c '… npm start 2>&1 \| tee -a log'` |
   |---|---|
   | `exit 1` | **0** |
   | вбито `SIGTERM` | **0** |
   | `exit 1`, але `set -o pipefail` | **1** ← доказ причини |
   | без пайпа взагалі | 1 (тобто `npm` код пропускає справно) |

   `PIPESTATUS=1 0` — код node **не втрачений**, він просто не стає кодом пайпа.
   🔴 **Наслідок:** аварійний вихід і штатну зупинку **неможливо розрізнити** за
   статусом. Тобто будь-який нагляд, що дивиться на код виходу, поводиться з `exit 1`
   ТОЧНО ТАК САМО, як із нашим `kill -TERM`, — а після `kill` процес підіймається
