## 1. Принцип: custom-логіка — своя, «загальне» — готове

| Потреба | Рішення | Чому |
|---|---|---|
| **Бізнес-логіка** (воронка, гроші, мінус-угоди, передані заявки, задачі, план/факт) | **Наш застосунок** | Жоден готовий BI не знає ваших правил (статуси Kommo, знімки оплат, РПК-воронка). Це ядро цінності. |

| **Бекапи** | Neon PITR + наш нічний CSV-дамп | Див. `BACKUP_RECOVERY.md`. Не пишемо своє сховище. |
| **Моніторинг аптайму** | **UptimeRobot** (безкоштовно) на `/api/health` | Пінгує щохвилини, шле алерт у Telegram/пошту, якщо впало. |
| **Сповіщення** | наш бекенд + **grammy** (вже є) у Telegram | Логіку знаємо ми; доставку робить Telegram. |

## 2. Metabase — ad-hoc аналітика (рекомендую)

**Що дає:** керівник/аналітик відкриває веб, кликами будує таблиці/графіки/дашборди по будь-яких полях, зберігає, шарить. Без звернень до розробника.

**Як підняти (≈1 год):**
1. Розгорнути Metabase (Docker: `metabase/metabase`, або хмара metabase.com).
2. Підключити **той самий Neon Postgres** — але **окремим read-only користувачем** (щоб аналітики не могли нічого змінити):
   ```sql
   CREATE ROLE metabase_ro LOGIN PASSWORD '…';
   GRANT CONNECT ON DATABASE neondb TO metabase_ro;
   GRANT USAGE ON SCHEMA public TO metabase_ro;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO metabase_ro;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO metabase_ro;
   ```
3. Готово — таблиці видно, будуються звіти.

**Межа:** Metabase бачить **сирі таблиці**, не наші «розумні» метрики (мінус-угоди, знімки оплат). Для складних правил — лишається наш дашборд. Metabase = «покопатись у даних», наш застосунок = «правильні бізнес-показники».

## 5. Пропозиції по Telegram-сповіщеннях (на обговорення)

Зараз ТГ уже є (сповіщення про передані заявки). Пропоную додати **адресні, дієві** тригери:

**Щоденні (ранкові дайджести):**
- **Тімліду о 08:30:** підсумок вчора по команді (оплати ₴, прорахунки, авто) + хто 0 активності 2+ дні.
- **Менеджеру о 09:00:** його план на сьогодні + відкриті задачі з дедлайном сьогодні.

**Подієві (миттєві):**
- 🔴 **Синк впав** (`consecutiveFailures ≥ 3`) → адміну.
- 💰 **Велика оплата** отримана (> порогу) → тімліду (мотивація).
- ⏰ **Боржник прострочив** понад ліміт → відповідальному менеджеру + тімліду.
- 🐢 **Угода застрягла** на етапі > N днів → менеджеру.
- 📉 **План відстає** від темпу (у середині місяця виконання < очікуваного %) → тімліду.

**Тижневі:**
- **Пн 09:00:** підсумок минулого тижня по кожному менеджеру (для наради).
- **Чт 09:00:** темп поточного тижня.

Механіка: ті самі cron-джоби в бекенді + grammy. Пороги — у `app_settings` (редагуються в Налаштуваннях). Скажи, які тригери вмикаємо — зроблю.

## 6b. Зʼєднання з БД: ПРЯМЕ, не через пулер Neon (рішення власника 05.08.2026)

`DATABASE_URL` вказує на **прямий** ендпоінт Neon, не на `-pooler`. Це свідомо, і
ось чому — щоб через півроку ніхто не «оптимізував» перехід:

- наш **read-only запобіжник** тестового харнесу стоїть на `PGOPTIONS=-c
  role=test_readonly`, який їде у **стартовому пакеті зʼєднання**. Пулер Neon
  працює в **transaction mode**, де сесійні опції не гарантовані — тобто
  запобіжник, що вже одного разу врятував прод від справжнього `DELETE`, став би
  «спрацьовує через раз, а виглядає завжди зеленим»;
- економити нема чого: `max_connections = 901`, пул застосунку **15**, реально в
  роботі одиниці зʼєднань (заміряно 05.08.2026).

🔴 Перехід на pooled-ендпоінт можливий ЛИШЕ разом із заміною механізму read-only
(наприклад, окремим користувачем БД замість ролі в опціях) — і це окреме рішення,
а не деталь конфігурації.

**Пул застосунку `max: 15`** (`db/pool.ts`). Був 6; `/overview` робить 35 запитів
на один запит екрана, тож четверо одночасних користувачів ставили 140 запитів у
чергу на 6 зʼєднань. Заміряно до/після: `/overview` ×4 8 546→4 550 мс, ×8
8 627→4 331 мс.

## 6c. Правила ЗАМІРІВ швидкодії

🔴 **МІНІМУМ ДВА ПРОГОНИ.** Розійшлись — шукати ЗОВНІШНЄ навантаження (тік синку,
паралельний набір тестів), а **не вибирати красивіший**. Реальний випадок
05.08.2026: перший «після»-замір дав `/overview ×4 = 10 500 мс` (гірше за «до»),
другий — 4 550 мс; різниця виявилась тіком `syncKommo`, що потрапив у вікно.
Подати перший як результат означало б відкотити правильну зміну; подати другий
без згадки про перший — прикрасити.

⚠️ Заміри «під навантаженням» усередині `test:prod` не є чистими: набір сам
вантажить сервер. Для порогів беруться ЧИСТІ заміри, у гейті — з запасом.

## 7. Процедура деплою в прод (порядок кроків)

Гілка розробки → прод-гілка `claude/friendly-galileo-8pijhl`. Деплоїти лише за явним токеном власника `ДЕПЛОЙ-ПРОД: ТАК`.

1. **FF-merge:** `git fetch origin <dev-branch>` → `git merge --ff-only origin/<dev-branch>` на прод-checkout (`/home/evraziat/uts.ua/dashboard`).
2. **Build BE:** `cd backend && npm run build` (tsc + копія `*.sql` у `dist/db`).
3. **Build FE:** `cd frontend && npm run build` (vite → `frontend/dist/`, новий хеш `index-*.js`).
4. **🔴 ОБОВʼЯЗКОВО — копія FE у веб-докрут.** Apache віддає **не** `frontend/dist`, а корінь `/home/evraziat/uts.ua/dashboard/` (там власні `index.html` + `assets/`). Vite пише лише в `frontend/dist`, тож без копії користувач бачить **старий** бандл, хоч API вже нове. Порядок (щоб index.html ніколи не показав на відсутній asset):
   - спершу нові asset-и: `cp -r frontend/dist/assets/. assets/`
   - статику: `cp frontend/dist/favicon.svg frontend/dist/icons.svg .`
   - **останнім** `index.html`: `cp frontend/dist/index.html index.html`
   - прибрати старий бандл — **ЛИШЕ якщо його імені НЕМАЄ в новому `index.html`**:
     ```
     for f in assets/index-*.js assets/index-*.css; do
       grep -q "$(basename "$f")" index.html || rm -f "$f"
     done
     ```
     🔴 **НЕ «якщо ім'я змінилось».** Vite хешує за ВМІСТОМ: правка лише в `.tsx`
     лишає css із ТИМ САМИМ іменем, і перевірка `OLD != NEW` не спрацьовує — а
     `rm assets/$OLDC` зносить рівно той файл, на який показує новий `index.html`.
     Так 05.08.2026 прод ~4 хвилини віддавав сторінку **без стилів** при зелених
     гейтах, health 200 і правильній версії. Спіймав скріншот приймання.
   - `index.html` віддається `no-cache` (див. `.htaccess`), тож новий хеш підхоплюється одразу.
5. **Рестарт node:** процес під панеллю adm.tools (`npm start` → `node dist/index.js`, PORT=3000). `kill -TERM <pid>` → панель авто-респавнить (новий pid за ~6с).
6. **Health:** `curl https://dashboard.uts.ua/api/health` = 200 ×N, `stale:false` (за потреби смикнути `POST /api/dashboard/sync` з admin-JWT — освіжає вотермарк без ризику подвійного синку).
7. **Перевірка бандла наживо:** `curl https://dashboard.uts.ua/index.html?cb=<ts>` має показати НОВИЙ `index-*.js`.

⚠️ Крок 4 — системний, не разовий: пропустиш → «ендпоінт віддає нове, а сайт показує старе» (реальний інцидент). BE-only деплой (FE не змінювався) → хеш той самий, крок 4 можна пропустити, але звірити хеш усе одно.
