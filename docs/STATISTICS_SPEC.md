## 0. Зафіксовані правила (нагадування, застосовані нижче)

- **R1 Тиждень** — у таблиці тиждень = **останній** день (неділя). У БД `period_start` = **понеділок** = `дата_з_таблиці − 6 днів`. Ніде не використовувати «останній день тижня».
- **R2 «самостійні» = Шевчук Назар** — розріз «самостійні» зливається з «Шевчук» у `team_lead='Шевчук Назар'`. Sum-метрики сумуються; avg-метрики перераховуються з базових. В авто-розрахунку угоди без менеджера → Шевчук.
- **R3 Легасі — ігнорувати повністю:** `Списки`, `ВЛТ`, `Лист28`, `Отдел продаж Месяц`, `Отдел продаж Неделя`, `Відділ маркетингу Месяц`, `Відділ маркетингу Неделя`, `Відділ логістики Месяц`, `Відділ логістики Неделя`.
- **R4 Плани — НЕ метрики розділу.** Колонки `План …` не імпортуються. План читається з наявного джерела (`plans`). Показуємо План / Факт / % поруч, але не дублюємо (див. §5).

## 2. Нормалізація (обов'язкова при імпорті)

- **Числа:** прибрати звичайні пробіли та **нерозривні** (U+00A0), десяткова кома → крапка, `%` прибрати й ділити на 100 для percent-метрик, порожнє → `NULL`. Приклад: `"5 587 692,20"` → `5587692.20`; `"45132%"` → аномалія (див. нижче).
- **Дати:** основний формат `DD.MM.YYYY`. Зустрічаються також `DD/MM/YYYY`, `D.M.YYYY` (без нулів), рік-друкарки. Парсер має покривати всі й **логувати** нерозпізнані, а не мовчки пропускати (крім явних аномалій §Аномалії).

## 3. Каталог метрик по відділах

`Джерело`: **auto** — рахується з Kommo/БД (CRM = істина); **manual** — лише ручний ввід; **derived** — формула з інших метрик того ж рядка.
Ключові таблиці БД для auto: `deals` (+ `pipeline_stage_map`, `payment_type`, `client_key`, `closed_at_kommo`), `managers`, `deal_stage_events`, `receivables`.
Базові визначення (з CLAUDE.md/KNOWLEDGE.md): **успішно** = `status_id=142` за `closed_at_kommo` у періоді; **оплата отримана** = снапшот `69716460`/`60412544`; **вислані рахунки** = снапшот `funnel_stage='invoiced'`; **поставлені авто** = вхід у «Авто працює» `69716300` (+`98470988`/`10937178`); **готівка** = `payment_type` = Наличные; повний цикл = пайплайни `8921932`+`155304`.
`aggregation` (для рядка «Разом» і R2): **sum** / **avg** / **last**.

## 4. Зведення: auto / manual / derived

- **Повністю auto (перерахунок з CRM):** `logistics` (4 з 5, +derived), `leadgen` (3 auto +2 derived), `intl` (auto +derived), `sales` (майже все auto, крім ВП-2/ВП-3), `marketing` (лідо-/рекл-ліди й виручка auto; бюджети manual).

## 5. Плани (R4) — джерело замість колонок «План …»

Плани вже зберігаються в таблиці **`plans`** (`backend/src/db/schema.sql:161`):

```
plans(manager_id → managers, plan_date DATE /*1-е число міс.*/,
      metric ∈ {lead_taken,quote_requested,approved,invoiced,paid,payment_amount},
      planned_value NUMERIC, UNIQUE(manager_id,plan_date,metric))
```

Також є `funnel_plans` (план воронки по етапах на місяць) і `kvp_plans`.

**Мапінг План↔Факт для розділу «Статистики»:**
- `sales.revenue_won` ↔ `plans.payment_amount` (сума по менеджерах тімліда за місяць). Це прямий і єдиний надійний план-факт.
- `sales.invoiced_amount` ↔ `plans.invoiced` (за наявності).
- `sales.payment_received` ↔ `plans.paid`.
- **Немає джерела плану** для: `avg_check`, `calls`, `managers_count`, усіх non-sales відділів. У шіті колонки `План Середній чек` / `План Кількість дзвінків` існують, але в дашборді відповідного джерела **нема**.
  → **Рішення для кроку 2 (ВП-9):** або (а) показувати План лише там, де він є в `plans` (решта — без плану), або (б) розширити `plans`/окрему таблицю планів статистик. Рекомендація: (а) на MVP — не тягнути неіснуючі плани, не порушувати R4.
- Тижневий план = місячний, пропорційно розкиданий по робочих днях тижня (як уже робить `PlansSection`).
