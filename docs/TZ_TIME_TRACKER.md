# ТЗ: Десктоп-трекер ефективного часу менеджера (UTS Time Tracker)

**Версія:** 1.0 · **Дата:** 10.07.2026 · **Замовник:** UTS, відділ продажів · **Статус:** до погодження

---

## 1. Мета

Побудувати систему обліку ефективного робочого часу менеджерів з продажу:

1. **Десктоп-агент** (macOS + Windows) — ставиться на компʼютер менеджера, трекає активність за компʼютером (активний час / простій), надсилає дані на сервер. **Це зона відповідальності підрядника.**
2. **Бекенд + дашборд** (уже існують: Node/Express + Postgres, React) — приймають дані агента і показують керівнику картину по кожному менеджеру/команді. **Це зона відповідальності команди UTS**; у цьому ТЗ описано як контракт, щоб обидві сторони працювали незалежно.

Межа відповідальності = **API-контракт з розділу 6**. Підрядник здає агента, який коректно говорить із цим API; серверну частину і візуалізацію робить UTS.

### Контекст продукту (важливо для розуміння)

- У UTS вже є аналітичний дашборд (`dashboard.uts.ua`): продажі, плани/факти, задачі KPI. CRM — Kommo, вона є єдиним джерелом даних про угоди.
- Філософія даних: **показувати як є, нічого не згладжувати**. Трекер має фіксувати сирі факти (активність/простій), а не «оцінки продуктивності» — інтерпретацію робить дашборд.
- Дашборд уже знає **реальну активність менеджера в CRM** (дзвінки, нотатки, чати з Kommo). Друга фаза продукту — накладання «час за компʼютером» × «активність у CRM», тому точність таймстемпів критична.

## 2. Терміни

| Термін | Визначення |
|---|---|
| **Активний інтервал** | Проміжок часу, коли за компʼютером є ввід (клавіатура/миша/трекпад) частіше, ніж поріг простою. |
| **Простій (idle)** | Немає жодного вводу довше за `idleThresholdSec` (дефолт **300 с**, конфігурується сервером). Простій починається з моменту ОСТАННЬОГО вводу, а не з моменту виявлення. |
| **Заблокований екран / сон** | Прирівнюється до простою. Lock screen, screensaver, sleep, вихід із сесії ОС — активність зупиняється миттєво (без очікування порога). |
| **Heartbeat** | Періодичний пакет даних агент → сервер (дефолт кожні **60 с**). |
| **Ефективний час** | Розраховується на сервері (не в агенті): Фаза 1 = сума активних інтервалів; Фаза 2 = активний час у «робочих» додатках + перетин з CRM-активністю. |
| **Пристрій (device)** | Конкретна інсталяція агента, привʼязана до одного менеджера довгоживучим токеном. |

Усі таймстемпи агент надсилає в **UTC, ISO-8601 з мілісекундами** (`2026-07-10T08:15:30.000Z`). Агрегацію по днях/тижнях сервер робить сам у таймзоні `Europe/Kyiv` — агенту про таймзони думати не треба.

## 4. Функціональні вимоги до агента

### 4.1 Перший запуск і авторизація

1. Вікно входу: **email + пароль** — ті самі облікові дані, що й для дашборда (у користувача вони вже є).
2. Агент викликає `POST /api/tracker/auth` (розділ 6.1) і отримує **довгоживучий device-токен**. Пароль ніде не зберігається; зберігається лише токен — у системному сховищі (macOS Keychain / Windows Credential Manager), НЕ у відкритому файлі.
3. Після входу агент показує: «Трекінг увімкнено для: {імʼя менеджера}».
4. Якщо сервер відповів `403 role_not_allowed` (наприклад, під адмін-логіном без привʼязки до менеджера) — показати зрозуміле повідомлення.
5. Один пристрій = один менеджер. Кнопка «Вийти» в налаштуваннях розриває привʼязку (токен інвалідовано на сервері).

### 4.2 Трекінг активності

1. Агент веде **стрічку інтервалів** двох станів: `active` та `idle`. Інтервал закривається при зміні стану **або** щохвилини (щоб довгий active різався на хвилинні шматки і втрачалось ≤ 1 хв даних при збої).
2. Джерело стану — глобальний лічильник часу з останнього вводу:
   - macOS: `CGEventSourceSecondsSinceLastEventType` (не потребує Accessibility-дозволу) або еквівалент.
   - Windows: `GetLastInputInfo`.
3. **Зміст вводу не перехоплюється і не логується.** Жодного кейлогінгу, жодних скріншотів. Фіксується лише факт «ввід був / не був» (опційно — кількість подій на хвилину як число `inputEvents`, без розшифровки).
4. Lock/sleep/logout → миттєве закриття active-інтервалу (події ОС: `NSWorkspace` notifications на mac, `WTSRegisterSessionNotification`/power events на Windows).
5. Переведення годинника, таймзони, літній час — не ламають трекінг (усе в UTC монотонно; для тривалостей використовувати monotonic clock, для міток — системний UTC).
6. **Фаза 2 (закладена в архітектуру, вмикається серверним конфігом `trackApps=true`):** до кожного active-інтервалу додається назва активного додатка (`app`, напр. `Google Chrome`) і заголовок вікна (`windowTitle`, напр. домен вкладки). На macOS для заголовків вікон потрібен дозвіл Screen Recording — агент має показати покроковий onboarding-екран для його надання; якщо дозволу нема, надсилати лише `app` без `windowTitle`, не падати.

### 4.3 Надсилання даних

1. `POST /api/tracker/heartbeat` кожні `heartbeatIntervalSec` (дефолт 60 с): усі закриті інтервали з часу останнього успішного надсилання, батчем.
2. **Офлайн-буфер обовʼязковий:** якщо сервера не видно — інтервали накопичуються в локальній черзі (SQLite або append-only файл) до **7 діб** і надсилаються при відновленні звʼязку, порціями ≤ 500 інтервалів. Дані не губляться при перезапуску агента/ОС.
3. **Ідемпотентність:** повторне надсилання того самого інтервалу не має дублювати дані (сервер дедуплікує по `(device, startedAt)` — але агент не повинен зловживати ретраями: expo backoff 5с → 10с → 30с → 60с → далі раз на хвилину).
4. Відповідь heartbeat може містити оновлений конфіг (`idleThresholdSec` тощо) — агент застосовує його без перезапуску.
5. `401` у відповідь = токен відкликано → агент зупиняє трекінг, показує вікно входу.
6. Увесь трафік — тільки HTTPS, базовий URL: `https://dashboard.uts.ua` (конфігурований для стейджингу).

### 4.4 UI агента (мінімальний, tray-first)

1. **Іконка в системному треї / menu bar** зі станом: 🟢 трекінг іде · ⚪ простій · 🔴 немає звʼязку з сервером (працює офлайн-буфер) · ⚠️ не авторизовано.
2. Клік → маленьке вікно: імʼя менеджера, статус, «активний час сьогодні» (локальний підрахунок, довідково), версія агента, кнопки «Налаштування», «Вийти з облікового запису».
3. **Кнопки «пауза трекінгу» НЕМАЄ.** Агент або працює, або менеджер виходить з акаунта (що видно керівнику як «агент офлайн»). Це свідоме продуктове рішення — прозорість замість ручних пауз.
4. Закриття вікна не завершує агент (лишається в треї). Quit — тільки через контекстне меню трею; після quit сервер природно побачить пристрій офлайн (немає heartbeat).

### 4.5 Прозорість для співробітника

1. При першому запуску — екран «Що збирає ця програма»: активний/неактивний час, (Фаза 2) назви додатків; що НЕ збирає: натискання клавіш, скріншоти, вміст листування.
2. Ця сама інформація доступна з меню «Про програму».

## 5. Серверна частина (робить UTS — довідково для підрядника)

Нові таблиці (Postgres, `backend/src/db/schema.sql`):

```sql
CREATE TABLE IF NOT EXISTS tracker_devices (
  id SERIAL PRIMARY KEY,
  manager_id INTEGER NOT NULL REFERENCES managers(id),
  token_hash TEXT NOT NULL UNIQUE,          -- sha256 від device-токена
  platform TEXT NOT NULL,                   -- 'macos' | 'windows'
  hostname TEXT,
  agent_version TEXT,
  last_seen_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  revoked_at TIMESTAMPTZ
);

CREATE TABLE IF NOT EXISTS tracker_intervals (
  id BIGSERIAL PRIMARY KEY,
  device_id INTEGER NOT NULL REFERENCES tracker_devices(id),
  manager_id INTEGER NOT NULL REFERENCES managers(id),
  started_at TIMESTAMPTZ NOT NULL,
  ended_at TIMESTAMPTZ NOT NULL,
  state TEXT NOT NULL CHECK (state IN ('active','idle')),
  app TEXT,                                 -- Фаза 2
  window_title TEXT,                        -- Фаза 2
  input_events INTEGER,
  UNIQUE (device_id, started_at)
);
CREATE INDEX IF NOT EXISTS idx_tracker_intervals_mgr_time
  ON tracker_intervals (manager_id, started_at);
```

Роут `backend/src/routes/tracker.ts`, монтується як `app.use("/api/tracker", trackerRouter)`. Авторизація heartbeat — окремим device-токеном (НЕ 12-годинним JWT дашборда). Дашборд: секція «Ефективний час» — по менеджеру/команді/дню: початок дня (перший active), кінець (останній active), чистий активний час, таймлайн-стрічка дня, індикатор «агент офлайн з HH:MM». Фаза 2 — перетин із `deals.last_activity_at`-подіями CRM.

## 6. API-контракт (обовʼязковий до виконання обома сторонами)

Базовий URL: `https://dashboard.uts.ua/api/tracker`. Content-Type: `application/json`.

### 6.1 `POST /auth` — привʼязка пристрою

Запит:
```json
{
  "email": "manager@uts.ua",
  "password": "•••",
  "device": { "platform": "macos", "hostname": "MacBook-Ivan", "agentVersion": "1.0.3" }
}
```
Відповіді:
- `200`:
```json
{
  "deviceToken": "hex-рядок 64 символи",
  "manager": { "id": 17, "name": "Іван Яцик" },
  "config": { "idleThresholdSec": 300, "heartbeatIntervalSec": 60, "trackApps": false }
}
```
- `401 {"error":"invalid_credentials"}` — невірні email/пароль.
- `403 {"error":"role_not_allowed"}` — обліковка без привʼязки до менеджера.
- `403 {"error":"account_disabled"}` — обліковку деактивовано.

### 6.2 `POST /heartbeat` — основний канал даних

Заголовок: `X-Tracker-Token: <deviceToken>`.

Запит:
```json
{
  "agentVersion": "1.0.3",
  "sentAt": "2026-07-10T08:16:00.000Z",
  "intervals": [
    { "startedAt": "2026-07-10T08:14:00.000Z", "endedAt": "2026-07-10T08:15:00.000Z",
      "state": "active", "inputEvents": 87, "app": null, "windowTitle": null },
    { "startedAt": "2026-07-10T08:15:00.000Z", "endedAt": "2026-07-10T08:16:00.000Z",
      "state": "idle" }
  ]
}
```
Правила: `intervals` може бути порожнім (heartbeat = «я живий»); ≤ 500 елементів; інтервали не перетинаються; `endedAt > startedAt`; тривалість інтервалу ≤ 10 хв (довші сервер відхиляє як аномалію).

Відповіді:
- `200 {"ok":true,"accepted":2,"config":{...}}` — `config` присутній, лише якщо змінився (агент застосовує).
- `200` з `accepted < надісланих` — дублікати тихо проігноровані (це норма при ретраях).
- `400 {"error":"validation","details":[...]}` — битий пейлоад; агент логує і НЕ ретраїть цей батч вічно (кладе в «отруєні» локально, шле решту).
- `401 {"error":"token_revoked"}` — розділ 4.3 п.5.
- `5xx` / мережева помилка → ретрай з backoff, батч лишається в черзі.

### 6.3 `POST /logout`

Заголовок `X-Tracker-Token`. Інвалідовує токен (`revoked_at = now()`). Відповідь `200 {"ok":true}`.

### 6.4 Правило еволюції контракту

Сервер може додавати нові поля у відповіді — агент має **ігнорувати незнайомі поля**, а не падати. Видалення/перейменування полів — тільки зі zміною мажорної версії API.

## 7. Нефункціональні вимоги

1. **Надійність:** крах агента не втрачає більше 1 хв даних (інтервали флашаться в локальну чергу щонайрідше раз на хвилину). Агент авто-рестартується вотчдогом ОС (launchd KeepAlive / Windows service або scheduled task за вибором підрядника — обґрунтувати).
2. **Безпека:** токен — тільки в системному сховищі; TLS обовʼязково; агент не відкриває жодного вхідного порту; логи агента без персональних даних (без заголовків вікон навіть у Фазі 2).
3. **Логи:** локальний ротований лог (≤ 10 МБ) для діагностики; рівень debug вмикається з налаштувань.
4. **Годинник:** якщо системний час стрибнув (NTP-корекція > 2 хв) — поточний інтервал закривається і починається новий; тривалості рахуються monotonic-годинником.

## 9. Етапи і приймання

### Етап 1 — MVP (предмет цього ТЗ)
Агент mac+win: авторизація, active/idle-трекінг, heartbeat, офлайн-буфер, трей-UI, автозапуск, автооновлення, інсталери через CI.

**Критерії приймання (демонструються на живому стенді, обидві ОС):**
1. Чиста інсталяція → вхід → інтервали зʼявляються в БД стейджа протягом 2 хв.
2. 5 хв без вводу → у БД idle-інтервал, що починається з моменту останнього вводу (похибка ≤ 5 с).
3. Lock екрана → active закривається миттєво (похибка ≤ 5 с). Sleep/wake — те саме.
4. Вимкнути мережу на 30 хв роботи → увімкнути → усі інтервали доїхали, без дублів і дірок.
5. Перезавантаження ОС → агент піднявся сам, продовжив трекінг, черга не втрачена.
6. Відкликання токена на сервері → агент протягом 2 хв показує вікно входу і не шле даних.
7. Добова робота: CPU ≤ 1% avg, RAM ≤ 150 МБ, немає витоку памʼяті.
8. Автооновлення: викладання нової версії в маніфест → агент оновився без участі користувача.
9. macOS-збірка нотаризована (Gatekeeper відкриває без обходів).

### Етап 2 — трекінг додатків (окрема оцінка, після MVP)
`app`/`windowTitle` в інтервалах, onboarding дозволів macOS, вимикання серверним конфігом.

### Етап 3 (UTS, поза скоупом підрядника)
Перетин із CRM-активністю Kommo, «ефективний час» у звіті КВП, кореляція з виручкою.

## Додаток А. Рішення, зафіксовані замовником

| Питання | Рішення |
|---|---|
| Скріншоти / кейлогінг | ❌ Ніколи. Тільки факт активності + (Фаза 2) назва додатка/вікна. |
| Ручна «пауза» в агенті | ❌ Немає. Або трекає, або logout (видно керівнику). |
| Хто рахує «ефективний час» | Сервер. Агент шле сирі інтервали і нічого не інтерпретує. |
| Таймзона звітності | `Europe/Kyiv` на сервері; агент — тільки UTC. |
| Один менеджер на кількох компʼютерах | Дозволено (кілька devices на manager_id); перетини інтервалів між пристроями сервер злиє при агрегації. |
