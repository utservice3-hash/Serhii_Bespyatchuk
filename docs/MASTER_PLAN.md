# ⛔ ПРОЧИТАЙ ПЕРЕД ТИМ, ЯК ЩОСЬ РОБИТИ

## Правило 1 — Виконуй РІВНО ОДИН крок за сесію

Після кожного кроку — **СТОП**, показуєш результат, чекаєш «далі».
Не роби два кроки поспіль. Не «заодно поправив». Кожен крок має стоп-критерій,
і в поспіху його легко «підтвердити» самообманом.

## Правило 2 — Заборонені циклічні перевірки

**НЕ ПРИЙМАЄТЬСЯ** перевірка виду «A = B ✓», де B — це те, чим ти щойно означив A.

Приклад реальної помилки, яку так пропустили:
> «Поставлені машини» означили як COUNT(успішних угод).
> Перевірили: `dispatched = successDeals = 949 ✓`.
> Це тавтологія, а не верифікація. Метрика була неправильна.

Приймається **тільки зовнішня звірка з трьох незалежних джерел:**

| Метрика | Наше | Ручний лист | Kommo API напряму |
|---|---|---|---|

## Правило 3 — Немає даних у CRM = БЛОКЕР, а не привід підмінити метрику

Якщо в CRM немає поля — скажи «блокер» і зупинись.
**Не «спрощуй» визначення метрики, щоб зійшлось.** Саме так з'явився баг з машинами.

## Правило 4 — Лист каже ЩО рахувати, CRM каже СКІЛЬКИ

Ручна Google-таблиця — це **перелік потрібних метрик**, а не істина в цифрах.
У ній є ручні похибки (доведено: 321 угода замість 320).
**CRM — єдине істинне джерело.** Не підганяй CRM під лист.
Але якщо в листі є окрема колонка — значить, бізнесу ця сутність **потрібна**.

```
Задача: одна таблиця фактів = єдине джерело правди для всіх цифр.
Зараз кожна секція має свою логіку → шість різних правд про «дохід».

   deal_id, event_date, stage, manager_id,
   team_id          -- команда на МОМЕНТ ПОДІЇ, не поточна (інакше історія попливе
                    -- при переході менеджера між командами)
   segment          -- 'new'|'regular'|'leadgen' (з глосарію, НЕ вигадувати)
   amount           -- МІНУСОВІ угоди зберігаються МІНУСОМ
   commission, is_cash

   -- ДВА ЯКОРІ (Правило №1) — обидва в таблиці, НІКОЛИ не змішуються:
   success_at       -- ЯКІР ПРОДАЖІВ: вхід у 142. Дохід, чек, конверсії, плани.
   unload_at        -- ЯКІР ФІНАНСІВ: дата акту (поле 463253). Cash flow, дебіторка.
   load_at          -- операційне поле, НЕ якір

   -- КАНАЛ (пріоритет: реактивація > реклама > повний цикл)
   channel          -- 'leadgen'|'ads'|'full_cycle'
   is_reactivated   -- реактивація Б'Є мітки!
   has_web_tags, traf_type, is_ads_accepted, pipeline

   UNIQUE (deal_id, stage)
   Індекси: (success_at, team_id), (success_at, manager_id), (unload_at), (channel, success_at)

2. ОДНА ДЖОБА buildFactTable.ts — інкрементальна, ідемпотентна (UPSERT),
   guard + таймаут, статус у /api/health.

3. ШАР ЗАПИТІВ backend/src/core/metrics.ts — ЄДИНЕ місце в проєкті з SQL по бізнес-метриках.
   Усі функції приймають однаковий фільтр:
     { from, to, teamIds?, managerIds?, segments?, granularity: 'day'|'week'|'month' }

   ⚠️ КОНВЕРСІЯ — це 6 метрик, а не одна:
     conversionCohort(channel) — ліди ПРИЙНЯТІ в періоді → скільки з них ЗРЕШТОЮ поставилось.
                                 ТІЛЬКИ вона йде в розгортку планів.
     conversionPeriod(channel) — поставлені в місяці ÷ прийняті в тому ж місяці.
                                 ТІЛЬКИ для оперативного звіту.
   channel ∈ ads | leadgen | full_cycle — у кожного СВІЙ знаменник:
     ads         → «Прийнято реклами»
     leadgen     → «Отримано заявок»
     full_cycle  → «Створено угод у Повному циклі»
   Функції conversion() БЕЗ параметра channel НЕ ІСНУЄ. Це заборонено.

4. Стару логіку НЕ ВИДАЛЯТИ. Вона живе паралельно до окремого кроку міграції.

- Edge cases — покажи, що робить ядро з кожним:
  а) угода без менеджера;
  б) менеджер перейшов в іншу команду в середині місяця;
  в) угода пройшла стадію двічі (повернули й знову провели);
  г) угода одночасно «постійний клієнт» і «від лідогенератора».

ЗАБОРОНЕНО:

```

   порівнює core/metrics.ts з Kommo API НАПРЯМУ.
   Виводить: метрика / період / наше / Kommo / дельта %.
   Exit code 1, якщо будь-яка дельта > 0.5%.

2. Джоба reconcileNightly — cron 05:00. Результат → таблиця reconciliation_runs.
   Дельта > 0.5% → алерт у Telegram-бот (він уже є).

   «Цифри звірені з CRM о 05:00 ✓» / червоний, якщо звірка впала.
