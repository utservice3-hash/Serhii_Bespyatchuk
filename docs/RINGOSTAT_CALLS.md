## Схема

```sql
CREATE TABLE IF NOT EXISTS ringostat_calls (
  uniqueid      TEXT PRIMARY KEY,          -- ключ Ringostat; унікальний (перевірено на 48 713)
  calldate      TIMESTAMPTZ NOT NULL,
  call_type     TEXT NOT NULL,             -- in | transitin | out | transitout
  disposition   TEXT,                      -- ANSWERED | VOICEMAIL | BUSY | NO ANSWER
  billsec       INTEGER NOT NULL DEFAULT 0,
  duration      INTEGER NOT NULL DEFAULT 0,
  caller        TEXT,                      -- сирий номер, як віддав Ringostat
  dst           TEXT,
  n_alias       TEXT,
  recording     TEXT,                      -- прямий URL (див. блок безпеки вище)
  employee_fio  TEXT,                      -- NULL у ~20% → «менеджер невідомий»
  manager_id    INTEGER REFERENCES managers(id),   -- NULL, якщо ПІБ немає або не змапився
  client_phone  TEXT,                      -- нормалізований номер КЛІЄНТА (не наш)
  client_key    TEXT,                      -- канонічний ключ; NULL = не звʼязалось
  synced_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_rc_client_key ON ringostat_calls(client_key, calldate DESC)
  WHERE client_key IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_rc_phone     ON ringostat_calls(client_phone, calldate DESC);
CREATE INDEX IF NOT EXISTS idx_rc_calldate  ON ringostat_calls(calldate DESC);
CREATE INDEX IF NOT EXISTS idx_rc_manager   ON ringostat_calls(manager_id, calldate DESC)
  WHERE manager_id IS NOT NULL;

-- Телефони контактів Kommo. Зараз у базі НЕМАЄ телефонів узагалі:
-- `deal_contacts` зберігає лише contact_id, а телефон існує тільки як
-- `client_key` фізособи. Без цієї таблиці звʼязати дзвінок із клієнтом нічим.
CREATE TABLE IF NOT EXISTS contact_phones (
  contact_id  BIGINT NOT NULL,
  phone       TEXT   NOT NULL,             -- нормалізований: лише цифри, з кодом країни
  is_main     BOOLEAN NOT NULL DEFAULT false,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (contact_id, phone)
);
CREATE INDEX IF NOT EXISTS idx_contact_phones_phone ON contact_phones(phone);
```

### Чому саме так

- **`uniqueid` як PK, а не сурогат.** Ringostat дає стабільний ключ, і він
  унікальний на всьому виміряному обсязі. Сурогат означав би власну логіку
  дедупу — тобто ще одне місце, де «те саме» може стати «схожим».
- **Сирі `caller`/`dst` зберігаємо ПОРУЧ із нормалізованим `client_phone`.**
  Нормалізація може виявитись неправильною; сирі поля дають змогу переграти
  її без повторного бекфілу. Той самий принцип, що `client_key_raw`.
- **`client_key` — похідна, не джерело.** Заповнюється звʼязкою і може
  перераховуватись; порожній `client_key` НЕ ховає дзвінок, а показує його
  як «клієнт не визначений».
- **`manager_id` окремо від `employee_fio`.** ПІБ — те, що прийшло; `manager_id` —
  результат мапінгу. Порожній `manager_id` при непорожньому ПІБ = ПІБ не змапився,
  і це видно, а не замовчується.

## Звʼязка номер → клієнт

1. Нормалізація номера: лишити цифри, привести до `380XXXXXXXXX`.
   Функція **одна** (`utils/phone.ts`), нею користуються і синк дзвінків, і
   бекфіл контактів — щоб «те саме» не стало «схожим» (урок `normalizeClientName`).
2. Номер клієнта = `caller` для `in`/`transitin`, `dst` для `out`/`transitout`.
   ⚠️ Для `out` `caller` містить SIP-логін (`utsua…`), а не номер — заміряно.
3. `client_phone` → `contact_phones.phone` → `contact_id` → `deal_contacts` →
   `deals.client_key`. Якщо контакт веде до кількох клієнтів — беремо той, у
   якого найсвіжіша угода, і **позначаємо неоднозначність**, а не мовчимо.

## План бекфілу

### Дзвінки — ПОМІСЯЧНО, з тротлінгом

- 12 місяців × 1 запит на місяць (API віддає весь місяць одним викликом:
  перевірено — липень 48 713 записів прийшли за один запит).
- Пауза **між місяцями**, не всередині: запитів мало, ризик — обсяг відповіді.
- Вотермарк по `calldate`, порціями ≤24 год (`processInChunks`, як в event-джобах) —
  щоб збій втрачав порцію, а не весь прохід.
- Запис у БД батчами по 500 із `ON CONFLICT (uniqueid) DO UPDATE`.
  🔴 **Дедуп батча обовʼязковий** — урок інциденту 03.08.2026.

### Контакти — ТІЛЬКИ ПІСЛЯ ЗАМІРУ КВОТИ NEON

🔴 **Стоп-умова.** Бекфіл 35 тис. угод (КРОК 1.4) випалив compute-квоту Neon за
годину і поклав прод у `sync:null`. Тут обсяг того ж порядку: контакти для
~146 тис. угод, батчами по 250 → ≈600 запитів до Kommo + стільки ж записів у БД.

Порядок: заміряти залишок квоти → **показати цифру власнику** → тільки потім
запускати, помісячно й у вікні, де синк не працює.

### Штатний синк

- Нова джоба `syncRingostatCalls` (окремо від наявної, що рахує агрегат) —
  **через `runJob`**, щоб банер її бачив.
- Частота: щогодини. Свіжість панелі дзвінків = ця частота, і це треба
  підписати на екрані, як зроблено для «отриманих коштів».
- **Агрегат «Статистик» не чіпається** — він живе як жив, на своєму запиті.

## 🟢 Політика: дзвінки ЗВІЛЬНЕНИХ приписуються їм (рішення власника 04.08.2026)

> «Історія має казати правду: „дзвонила конкретна людина (звільнена)" корисніше
> за „невідомо"».

`linkCalls` більше НЕ фільтрує `managers.is_active`. Замір після зміни:

| | дзвінків | % від 415 441 |
|---|---:|---:|
| менеджер визначено ДО зміни | 274 369 | 66.0% |
| **після** | **298 657** | **71.9%** |
| з них приписано звільненим | 24 288 | 5.8% |
| лишилось «менеджер невідомий» | 116 784 | 28.1% |
| — бо Ringostat не дав `employee_fio` | 113 662 | 27.4% |
| — бо ПІБ немає в `managers` взагалі | 3 122 | 0.8% |

**Три межі, які тримають це рішення чесним:**

1. **Колізія імені → пріоритет активному.** `DISTINCT ON (k) … ORDER BY k,
   is_active DESC, id`. Після зняття фільтра обидва рядки однієї людини
   (активний + деактивований) потрапляють у вибірку, тож пріоритет став
   ОБОВʼЯЗКОВИМ, а не запобіжним. Гейт `#27d`.
2. **Екрани ОЦІНКИ деактивованих не показують — і це перевірено поведінкою, не
   grep-ом.** Деактивована «Мельник Лілія» має 7 виграних угод за 90 днів, тобто
   було кого шукати, — і вона не зʼявляється ані в `successByMgr` (грошовий
   рейтинг), ані в `stuckDealsGrouped`. Звʼязка дзвінка — це ІСТОРІЯ, не рейтинг.
3. **«Приписуємо звільненим» ≠ «приписуємо навмання».** ПІБ, якого немає в
   `managers`, і далі лишається `NULL` — гейт `#27f` (дзеркало заборони до
   дозволу `#27e`). Саботаж перевірено в обидва боки: повернути `is_active` →
   червоніє `#27e`; прибрати звірку ключа → червоніють `#27c/d/e/f`.

### ⚠️ ВИМОГА ДО МАЙБУТНЬОГО ЕКРАНА ДЗВІНКІВ

Екрана історії дзвінків **ще немає**. Коли зʼявиться (картка клієнта, стрічка
дзвінків, будь-який список із менеджером) — **звільнений мусить бути підписаний
звільненим**. Інакше рішення вище перетворює правду на нову брехню: людина, що
пішла пів року тому, читатиметься як діюча.

Мінімум: віддавати поруч із `manager_id` прапорець `is_active` і малювати
приглушену плашку «звільнений» біля імені. НЕ ховати такі рядки — сенс рішення
саме в тому, щоб історія була повною.

## 📦 СХОВИЩЕ: 341 МБ → 1.17 ГБ. Куди пішло (замір 04.08.2026)

Очікували +70-80 МБ. Вийшло +830 МБ. Розбір показав ДВІ різні причини, і лише
одна з них — дані.

### Що каже сам Neon (`/projects/{id}`)

| | |
|---|---:|
| `synthetic_storage_size` (те, що в білінгу) | **1118.2 МБ** |
| логічний розмір гілки `production` | **639.2 МБ** |
| **різниця = історія (PITR/WAL)** | **479.0 МБ** |
| `history_retention_seconds` | **21 600 = 6 годин** |

**🟢 479 МБ — це НЕ дані і вони розсмокчуться самі.** Вікно історії 6 годин: щойно
churn бекфілів вийде за нього, Neon їх відпустить. Нічого робити не треба.

Звідки стільки churn: три прогони `linkCalls` переписали ~483 тис. версій рядків
(346 873 + 111 366 + 24 288 + 62 — більше, ніж рядків у таблиці), а бекфіл
контактів торкнувся ВСІХ 164 707 лінків `deal_contacts`, включно з 57 тис. уже
наявних (`ON CONFLICT DO UPDATE` переписує рядок навіть без змін).

### Важелі (НЕ застосовані — рішення власника)

1. **Нічого не робити.** 479 МБ історії підуть самі за 6 годин. Це найбільша
   частина розриву.
2. **4 індекси з 5 просканували рівно ОДИН раз** (`idx_rc_phone` 28.6 МБ,
   `idx_rc_client_key` 23.1, `idx_rc_calldate` 15.9, `idx_rc_manager` 13.8 —
   разом **81.4 МБ**). Працює лише `ringostat_calls_pkey` (416 104 скани). Вони
   зроблені під екран історії дзвінків, якого **ще немає**.
   ⚠️ Дропати наосліп НЕ пропоную: `idx_rc_phone` може обслуговувати `UPDATE`
   у `linkCalls`, і «1 скан» цього не спростовує (UPDATE ходить іншим шляхом).
   Перед видаленням — заміряти `EXPLAIN` самої джоби.
3. **`VACUUM FULL ringostat_calls`** віддав би ~90 МБ мертвого місця, але бере
   ексклюзивний лок. Не під час синку.
4. **`recording` зберігати ТРЕБА.** Перевірено: посилання НЕ виводиться з
   `uniqueid` — там власне імʼя файлу і `?token=`. Із 415 441 рядка збігається з
   шаблоном `.../recordings/<uniqueid>` рівно **0**. Тобто «не зберігати, а
   складати на льоту» — неробочий варіант, хоч і виглядає привабливо.
