## 1. Що з Хурми беремо, а що ні

**Беремо (Іван: «мастхев»):**
- вакансії окремим списком зі статусами й кількістю кандидатів; вакансія обовʼязкова в кандидата;
- шлях кандидата: новий → перше повідомлення → призначено інтервʼю → інтервʼю → відправлено офер → прийнято офер;
- відмова як дія з причиною у двох групах + «Додати в резерв»;
- резерв кандидатів;
- контакти: телефон (ключ дублів), пошта, Telegram; кнопки Telegram / Viber / WhatsApp;
- файли-докази в картці (скриншот переписки);
- воронка з відсотками за вакансією / періодом / джерелом, частка відмов кандидата й компанії.

**Не беремо (Іван: «не потрібно»):** контрольна панель, «Компанія», календар, кілька
рекрутерів на вакансію, теги, команди у фільтрах.

**Вже є в нас і збігається з Хурмою:** ключ дублів за телефоном; при повторному додаванні —
посилання на наявну картку з її статусом.

### Прохід 2 · Кандидат отримує акаунт; тімлід веде навчання

**Мета.** Сергій: «вибрав статус кандидат — у людини вже є логін до дашборду, бачить лише
навчання»; тімлід бачить прогрес і сам переводить у «менеджер».

**(а) Файли**
- `core/hiring.ts` — при переході в «кандидат + команда» створити користувача з роллю
  `candidate` через наявний `userService` (НЕ новий механізм), привʼязати `user_id` до кандидата.
- доставка входу: одноразове посилання/код у Telegram кандидата (бот підпису вже вміє писати
  людям) — **рішення власника**, див. питання 5.
- джоба деактивації: кандидат без входу / без прогресу N днів → `is_active=false` з причиною.
  Реєстрація в `MONITORED_JOBS`.
- «Навчання»: **екран прогресу для тімліда й рекрутера** (сьогодні його немає) — або в межах
  цього проходу, або разом із ТЗ-2 «Навчання» (інша сесія; узгодити, щоб не робити двічі).
- перехід у «менеджер»: зміна `role_override` candidate → manager + запис у реєстр
  співробітників (прохід 4; до нього — лише зміна ролі).

**(б) Дані.** Нова колонка `user_id` у кандидата. Акаунти створюються в `users` — **це запис у
бойову таблицю, яку читають Налаштування, матриця доступу, синк**. Відкат коду акаунтів не
прибирає.

**(в) Не робимо:** офер із шаблону (прохід 3), обхідний лист, реєстр співробітників.

**(г) Що може зламатись:** `provisionUsers` копіює `managers.is_active` на `users` — акаунт
кандидата без `manager_id` не має під нього потрапити; `#443`; `#15`; вкладка «Користувачі» в
Налаштуваннях (зʼявляться кандидати — фільтр за роллю); `activeManagerSql`.

**(д) Гейти**
| гейт | червоніє, якщо |
|---|---|
| перехід у «кандидат» створює РІВНО один акаунт з роллю candidate; повтор — не створює другий | створювати на кожен перехід |
| акаунт кандидата бачить лише навчання й документи | дати роль manager одразу |
| деактивація через N днів: N−1 — активний, N+1 — ні; повернення кандидата реактивує | звести до «завжди деактивувати» |
| тімлід переводить у «менеджер» лише свого кандидата | зняти перевірку команди |
| пароль не повертається в API і не пишеться в історію | покласти пароль у подію |

**(е) Приймання:** кандидат у scratch-середовищі отримує вхід, бачить два екрани; тімлід бачить
його прогрес; через N днів без входу — неактивний. Скріншоти кожного кроку.
**(ж) Обсяг:** ~500 бекенд, ~300 тести, ~400 фронт (без екрана прогресу); 1.5 дні.

### Прохід 3 · Шаблони документів: офер РПК/РНК і договір із клієнтом

**Мета.** Один механізм: шаблон із полями → заповнений документ → «Документи» → підпис.
Використовують Іван (офер при «кандидат + команда») і менеджери (договір по угоді).

**(а) Файли**
- `db/schema.sql` — шаблони (назва, тип: офер / договір, файл-джерело, перелік полів із
  джерелом кожного), згенеровані документи (шаблон, версія шаблону, значення полів, хто, коли).
- **нове** ядро підстановки: DOCX-шаблон із мітками `{{поле}}` → DOCX/PDF. Потрібна бібліотека
  рендеру DOCX (нова залежність — **рішення**, див. питання 7).
- джерела полів:
  - **офер:** ПІБ, паспорт, ІПН, дата, команда, посада — з картки кандидата (нові поля паспорта
    й ІПН у кандидата — **персональні дані**, доступ лише HR/керівництво);
  - **договір:** номер = номер угоди; дата = дата формування; наша сторона — з
    `bank_accounts` за полем угоди «На яку компанію надходять кошти»; клієнт — назва й ЄДРПОУ з
    `kommo_companies`; **порожні поля** (підписант і підстава, адреса, IBAN, ІПН, телефон, пошта,
    податковий статус) — питання 3.
- `routes/documents.ts` — «Створити з шаблону»; документ лягає в `offer` (адресат — кандидат)
  або в новий розділ договорів угоди. Координувати з сесією «Документи».
- `HiringCandidates.tsx` — кнопка «Сформувати офер»; у картці угоди — «Сформувати договір».

**(б) Дані.** Нові таблиці; файли — у теці документів (вже в нічному бекапі, `#446`).

**(в) Не робимо:** підпис клієнтом (КЕП / Дія / Вчасно — окреме рішення з
`PLAN_DOCUMENTS_V2`), редактор шаблонів у браузері (шаблон завантажується файлом).

**(г) Що може зламатись:** підпис привʼязаний до sha256 версії — перегенерація має створювати
НОВУ версію, а не перезаписувати файл; `canSeeDocument` для розділу offer; бекап.

**(д) Гейти**
| гейт | червоніє, якщо |
|---|---|
| кожна мітка шаблону має джерело; немає значення — документ НЕ формується й називає поле | підставити порожнє мовчки |
| наша сторона договору — та, що в полі угоди (UTS ≠ Автомув) | брати першу юрособу |

| паспорт/ІПН кандидата не віддаються тімліду й менеджеру | віддати картку повністю |

**(е) Приймання:** офер РПК для тестового кандидата і договір для угоди `61896127` — порівняти
з наданим PDF поле за полем (таблицею «шаблон / згенеровано»).
**(ж) Обсяг:** ~700 бекенд, ~300 тести, ~400 фронт; 2–2.5 дні. **Блокери:** файли шаблонів

**(г)** `depstats`: ручні HR-метрики в каталозі статистик (`statistics/catalog.ts`) можуть
задублювати — вирішити, чи замінюємо їх.
**(д)** Гейти: помісячна плинність за 2025 == таблиця після імпорту (зовнішня звірка);
майбутній місяць не 0, а «ще не настав»; exit без дати звільнення не зберігається.
**(е)** Таблиця «місяць / таблиця / дашборд / Δ» за 2025–2026.
**(ж)** ~400 бекенд, ~200 тести, ~600 фронт; 1.5 дні. **Блокер:** питання 8.

### Прохід 6 · Зведення: воронка як у Хурмі, вакансії

**(а)** Плитки й воронка за період / вакансією / джерелом; частки відмов кандидата й компанії;
таблиця етапів «кандидати / конверсія / відносна конверсія / відмови»; закриті вакансії по місяцях;
співробітники за посадами; звільнені за причинами.
**(д)** Гейти: Σ етапів по вакансіях == усього; відмови кандидата + компанії == усього відмов;
відносна конверсія — від попереднього етапу, а не від першого.
**(е)** Звірка з «Загальний дашборд NEW» за березень 2026 (у таблиці ручні числа —
розбіжності показуємо, не підганяємо).
**(ж)** ~350 бекенд, ~150 тести, ~600 фронт; 1.5 дні.

### Прохід 7 · Інтеграції: work.ua і tl;dv

- **work.ua:** відгуки на вакансії → кандидати «новий» з резюме посиланням, джерело «work.ua»,
  дублі за телефоном. **Блокер:** доступ до API work.ua для роботодавця (чи є в UTS, які права).
- **tl;dv:** запис співбесіди в рядок графіка автоматично; оцінка кандидата штучним інтелектом
  за транскриптом (модель Claude). **Блокери:** токен tl;dv; рішення про зберігання транскриптів
  (персональні дані) і вартість.
- **(д)** Гейти: повторний відгук того самого номера не створює дубля; без токена — чесний
  «не підключено», а не порожній список.
- **(ж)** 1–1.5 дні на кожну, після доступів.
