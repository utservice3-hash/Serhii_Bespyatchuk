# UTS Dashboard — довідка проєкту

Аналітичний дашборд для відділу продажів логістичних послуг (CRM = Kommo).
Стек: Node/Express + Postgres (backend), React + Vite + recharts (frontend).

> 🧭 **Нова сесія / продовження роботи → почни з `docs/HANDOFF.md`** (точка входу: стан, черга, деплой, граблі). Відновлення даних — `docs/BACKUP_RECOVERY.md`. Інфраструктура/готові рішення — `docs/INFRASTRUCTURE.md`.

> 💡 **Робочий стиль (за проханням власника):** коли надходить задача під реалізацію — виконати її, а потім ДОДАТКОВО запропонувати, як покращити / що додати / що змінити (погляд керівника КВП, а не лише мовчазне виконання).

> 🎯 **ФІЛОСОФІЯ ДАНИХ (незмінна, для всіх правок і нововведень):** **CRM (Kommo) — єдине істинне джерело даних; дашборд — його дзеркало.** Мета — максимальна деталізація і точність. Будь-яка цифра має відтворюватись із CRM і збігатися з нею; якщо є розбіжність — це баг дашборду, а не «інша думка». Не вигадувати метрики, не згладжувати аномалії — показувати як є і підсвічувати сумнівні дані.

## Ключові бізнес-правила

- **Отримані кошти = Успішно реалізовано (статус 142, за датою закриття `closed_at_kommo` в періоді) + Оплата отримана (статуси `69716460`/`60412544`, ЗНІМОК поточного етапу, без фільтра дати).** Це ОДНА логіка скрізь: картка «Отримані кошти», byTeam, topManagers, Факт, рейтинг команд.
  - Чому різні бази: «Успішна угода» — фінальний статус (накопичується назавжди, ~37млн за весь час), тому рахуємо лише закриті в періоді. «Оплата отримана» — транзитний етап (угоди проходять далі), тому це знімок «скільки зараз там».
  - Звірка з CRM (червень 2026): успішно за місяць ≈ 670 угод/1.81млн; оплата отримана знімок ≈ 127/0.52млн; разом ≈ 2.33млн. Збігається з колонками CRM.
- **Угоди (KPI «рахунок→реалізовано»)** = `funnel_stage IN ('invoiced','paid')`, за датою створення.
- **Воронка продажів** = лише пайплайни «Перевозки повний цикл»: `8921932` (New) + `155304` (старий).
- **Конверсія** розділена: реклама (`lead_channel='ad'`) і лідоген (`lead_channel='leadgen'`) — оплачені/ліди по каналу.
  - **Реатрибуція каналів = «останній дотик» ПО КОЖНІЙ угоді** (`reclassifyAdChannel` щосинку по всій таблиці, ідемпотентна, вміє знижувати канал; правило власника 08.07.2026 — лідген може реактивувати клієнта З РЕКЛАМИ і передати в прорахунок): канал угоди повного циклу = найсвіжіший дотик клієнта (`client_key`) ПЕРЕД створенням угоди (+3 дні слеку). **Лідоген-дотик** = передача (`lead_transfer_events`) / вхід у «Нова заявка від лідогенератора» `69716164`/`63019380` (`deal_stage_events`) / лід зараз на цьому етапі. **Рекламний дотик** = створення ліда Кваліфікації (`8921928`/`7336928`) БЕЗ лідоген-маркерів (крім 143). Поле «Лидогенератор» на угоді завжди → leadgen; фолбек — utm/«Источник клиента» → ad. Старі рекламні угоди клієнта лишаються ad, угоди після лідоген-передачі → leadgen.
- **Нові клієнти** = перша оплата за всю історію припадає на період. **Постійні клієнти** = 2+ оплачених перевезень (lifetime) **ТА активні** (замовляли в межах `sleepingWindowMonths`, дефолт 6міс, або є в дебіторці). Замовклі з минулих років падають у sleeping/lost для реактивації, а не висять у «постійних». У `/loyalty` кожен клієнт рахується ОДИН раз і кріпиться до основного менеджера (найбільше оплат) — крос-менеджерських дублів нема. **Тип клієнта**: компанія (ключ по нормалізованій назві) vs фізособа (ключ по телефону — ідентифікатор). **Нормалізація client_key**: `normalizeClientName` join('') (без пробілів) — spacing/апостроф варіанти однієї компанії дають ОДИН ключ («СМАР ТЕКС»/«СМАРТЕКС»→"смартекс"). Бекфіл виконано (`jobs/backfillClientKey`, 23к угод). ⚠️ ЩЕ НЕ злиті: назва↔телефон (Глобал Фудс з телефонним ключем), контакт-людина при компанії (Максим Смар Текс), Latin/Cyrillic гомогліфи в юр.назві (ВIДПОВIДАЛЬНIСТЮ з латинською I → фраза ТОВ не стрипається), різниця у зайвому слові — потребують гомогліф-нормалізації / фаззі-матчу (відкладено, ризиковано авто-мерджити).
- **План по постійних клієнтах** (`RepeatPlanGrid` у розділі loyalty, admin/team_lead): місячний таргет виручки З постійних по менеджеру (`plans` metric=`repeat_payment_amount`). Факт = отримані кошти (успішно 142 закрито в міс + оплата снапшот) від клієнтів із 2+ lifetime-оплатами. Залишок динамічно розкидається на майбутні робочі дні. Ендпоінт `/dashboard/repeat-plans-grid`.
  - **Плани по КОЖНОМУ постійному клієнту** (розкрити менеджера): рядок на клієнта як у ручному файлі КВП. Клієнт зʼявляється в таблиці **АВТОМАТИЧНО**, щойно має 2+ оплати lifetime і активний — список тягнеться з CRM (не вручну), кріпиться до основного менеджера. Табл. `repeat_client_plans` (PK client_key+month) зберігає ПЛАН+метадані: `plan` (місячний, тижнева декомпозиція), `forecast` (same/up/down), `realization_pct`, `international`, `we_do`, `call_link`, `comment`, + колонки `orders`/`revenue`/`lastPaid`/`lastActivity`/тип у відповіді. Факт по тижнях авто = «Успішно» 142 закрито в тижні; місячний факт +оплата снапшот. Перемикач «💤 замовклі» (`includeInactive`) показує постійних поза активним вікном.
    - **Воркфлоу затвердження**: план по клієнту ставить **менеджер** (бачить лише свій рядок і своїх клієнтів) → «Надіслати» = `status='pending'`; **тімлід/адмін** тисне «Затвердити» → `status='approved'` (їхні правки одразу approved). Ендпоінти `POST /dashboard/repeat-client-plan` (рядок шлеться повністю; менеджер→pending, тімлід→approved) + `POST /dashboard/repeat-client-plan/approve`. `repeat_client_plans.status/approved_by/approved_at`.
- **Дебіторка — деталізація рахунків**: клік на клієнта → неоплачені рахунки (№/дата/сума/лінк) з вкладки «выгрузка» (gid=0) файлу дебіторки. Табл. `receivable_invoices` (TRUNCATE+insert у `syncReceivables` разом із `receivables`), ендпоінт `GET /dashboard/receivables/invoices?clientKey=` (role-scoped). Коментар+дата оплати тімліда — `receivable_notes`.
- **Готівкові клієнти в дебіторці (CRM, не з файлу)**: готівкові платять кешем → їх борг не в безнал-файлі. `syncReceivables.insertCashReceivables` (у тій самій транзакції після листа) додає угоди повного циклу, де рахунок виставлено, але кошти ЩЕ не надійшли = НЕ 142/`69716460`/`60412544` І (`funnel_stage IN approved/invoiced` АБО AVTO `69716300/98470988/10937178`), price>0. Список у `CASH_RECEIVABLE_CLIENTS` (label+усі client_key варіанти). Рядок перераховується щосинку → угода зникає автоматом, щойно перейшла в «оплата отримана»/«успішно». Кожна угода = рядок у `receivable_invoices` з лінком на угоду в Kommo. **Сума = ПРИХОД, не бюджет**: беремо `extractIncomeAmount` (поле «Розрахунок приходів» `2097649`, фолбек «Приход 1» `2097627`) через `fetchLeadsByIds` — бюджет (`price`) сильно занижує реальний дохід готівкового (МГЕР бюджет 52.5к vs приход 221к). Перший: МГЕР (`мгер`/`0668339283`, Семенюк, ~221к приходу / 9 угод).
- **Передані заявки → Успішно** (`overview.transferred`): виключає лідоген-команди (передача = лідоген→продажі, не всередині лідогену); «успішно» = передана заявка, чий КЛІЄНТ дійшов до виграної угоди повного циклу (крос-пайплайн by client_key, як lead-quality) — НЕ всі виграні угоди команди (давало конверсію >100%).
- **Лідогенерація**: пайплайни Продзвін `8921936`/`7337048` + Реактивація `8921948`. Команда лідогенів — назва містить «лідоген».

- **Дебіторка ↔ Реактивація**: клієнт у `receivables` (активний боржник) НЕ потрапляє в реактивацію (ні в loyalty sleeping/lost, ні в `reactivateLeads`).

- **⚠️ Дати ЗАВЖДИ по-київськи, включно з обома кінцями**: усі фільтри періоду = `(col AT TIME ZONE 'Europe/Kyiv')::date BETWEEN $from AND $to`. Був баг: `col <= $to` (рядок→00:00 UTC) РІЗАВ увесь останній день місяця (для червня ховав 251 угоду). Виправлено скрізь — не повертати `col <= $to`.

- **📖 СЛОВНИК МЕТРИК — НОРМАТИВНИЙ**: `docs/METRICS_GLOSSARY.md` (одне визначення на метрику; код розходиться зі словником = баг коду). **Правило №1 — ДВА ЯКОРІ**: ПРОДАЖІ = дата переходу в «Успішно реалізовано» (гроші, машини, чек, конверсії, плани); ФІНАНСИ = дата акту/розвантаження (окремий блок, не змішувати в одній таблиці, підписувати якір). **«Поставлені машини» = угоди, що перейшли в успіх у періоді** (= успішні угоди; снапшот-проксі і подієвий варіанти ВИДАЛЕНО звідусіль 13.07). **adSources живе в БД** (сид у schema.sql, журнал `ad_sources_log`; дефолтів у коді НЕМАЄ — порожньо = конфіг-помилка). Історичні ряди: знімки не відтворюються → чисельник = успішно. Повний глосарій назв/формул — `docs/METRICS_GLOSSARY.md` (одна суть = одна назва).

Колонки: **План (статичний, редаг.)**, **Факт** (успішно 142 закрито в міс + оплата снапшот), **Перенесені** (`monthly_carryover_mgr`), **Очікувані** (снапшот з етапу `invoiced` = «Виставлено рахунок»), **Залишок**, тижні, на день. **Декомпозиція ДИНАМІЧНА**: залишок = max(0, план−факт) розкидається на МАЙБУТНІ робочі дні → цілі авто-зменшуються у міру виконання (минулі дні не рахуються). ## Джоби (backend/src/jobs)

- `syncKommo` — **кожні 5хв** (угоди, менеджери). ⚠️ Тягне контакти/компанії ЛИШЕ по id угод вікна (`fetchContactsByIds`/`fetchCompaniesByIds`, батчі по 250) — `fetchAllContacts/fetchAllCompanies` OOM-вбивали job (заморозка даних). НЕ повертати fetchAll*.
- `syncReceivables` — кожні 30хв (Google Sheet дебіторки, `TRUNCATE receivables` + insert).
- `syncNews` — щодня 08:00.
- `evaluateKpiTasks` — щодня 07:00: тягне факт із CRM і автозакриває KPI-задачі (план тімліда).
- `reactivateLeads --write --limit=N` — створення лідів реактивації (компанії з телефоном, 3+ перевезень, лапсуючі >3міс, НЕ боржники, round-robin лідогенам).
- `syncStageEvents` — **кожні 10хв + старт** (події `lead_status_changed` → `deal_stage_events`, дати входу в етапи). Backfill: `--months=N`. Ретеншн 24 міс (04:30). ⚠️ Kommo events API капить пагінацію ~20тис/запит — глибокий backfill неповний.
- `syncTransfers` — **кожні 10хв + старт** (події `entity_responsible_changed` на лідах Кваліфікації `8921928`/`7336928` → `lead_transfer_events` = «передані заявки»). Backfill `--months=N`.
- `syncDealActivity` — **кожні 10хв + старт** (нотатки Kommo `/leads/notes` → `deals.last_activity_at` = остання РЕАЛЬНА людська активність: `call_in/out`, `sms_in/out`, `common`, `chat_message` з `created_by <> 0`). Salesbot (`created_by 0`) НЕ рахується. Watermark `sync_state.last_activity_note_at`. Backfill `--months=N`. Живить «застряглі угоди».
- `syncAdBudget` — **щогодини (:15) + старт** (Google-таблиця реклами `AD_BUDGET_SHEET_URL`/дефолт у config → `ad_budget_daily`: `budget_plan`, `budget_fact`, `conversions`, `clicks` по днях). Парсить денні рядки з ключем YYYYMMDD (кол.1), план=кол.3, факт=кол.4, конверсії=кол.10. Накопичує історію (минулі місяці лишаються). Живить Реклама-бюджет у Звіті КВП. ⚠️ Таблиця має лише поточний місяць — минулі місяці зʼявляються з накопиченням.
- `snapshotCarryover` — **1-го числа 00:00 + старт** (знімок «перенесених» угод у роботі → `monthly_carryover`, фіксується раз/міс).
- `recomputeStatistics` — **щогодини (:25) + старт** (розділ «Статистики (відділи)»: sales auto-метрики поточного міс+тижня → `statistics_values`, UPSERT). Guard+таймаут. Статус у `/api/health.statistics`. Бекфіл історії — `scripts/backfillStatistics.ts` (вручну).
- `syncFirstTouch` — **кожні 30хв + старт** (лист «Перший дотик» AI-транскрибації → `first_touch_analysis`, показник «озвучено ціну в перший дотик» у Звіті).
- `syncRingostatCalls` — **щогодини (:35) + старт** (Ringostat API → `sales.calls` рівня відділу, результативні = `billsec>0`).
- `syncCashIncome` — **раз на 3 год (:50) + старт** (приход по готівкових 142-угодах поточного міс+тижня через `fetchLeadsByIds`/`extractIncomeAmount` → `sales.cash_deals_amount` auto per team_lead; легке навантаження на Kommo).
- `backupDb` — **щодня 03:00** (незалежний бекап: кожна таблиця → gzip-CSV через `COPY` у `dashboard/backups/uts_*`, ретенція 14). Ручний: `npm run backup`. БД на **Neon** (PITR — основний бекап). Деталі й відновлення — `docs/BACKUP_RECOVERY.md`. ⚠️ на проді деплой — `npm install` БЕЗ `--omit=dev` (потрібен tsc для build).
- Фронт **автооновлюється кожні 5хв** (`refreshNonce` у Dashboard.tsx) — без перезавантаження.

## Надійність та моніторинг синку

- `syncKommo` захищений: in-process guard (пропуск, якщо попередній ще йде), таймаут 60с на запит до Kommo (`AbortController`), watermark рухається ЛИШЕ при успіху (помилка → наступний прохід повторює вікно). Синк при старті бекенду + **нічна реконсиляція 04:00** (`syncKommo({reconcileDays:45})` — лікує гепи, бо інкремент не перетягує угоди, змінені під час минулих збоїв).
- Стан синку в `sync_state` (`last_success_at, last_error, last_deal_count, consecutive_failures, last_event_at, last_transfer_at`). Видно в `/api/health` + `/dashboard/sync-status` + індикатор у «Налаштуваннях» і **кнопка «🔄 Синхронізувати зараз»** в «Огляді» та «Налаштуваннях** (`POST /dashboard/sync`, admin/тімлід).
- Причина колишньої «заморозки»: синк падав/зависав і мовчки стояв годинами — тепер видно й лікується.

## Статистики (відділи) — `depstats`, авто-заміна Google-таблиці показників

Заміна ручної таблиці «UTS Показники для статистик» (Sheet `1F_lTE7a…`). 6 відділів (виключено Міжнародку/Авіа-Море/Тендери — немає робочого пайплайну/закрито). Гібрид: sales-метрики з CRM (auto), решта — imported/manual. Специфікація — `docs/STATISTICS_SPEC.md` (§0-БІС = ухвалені рішення), звірка — `docs/STATISTICS_RECONCILIATION.md`.
- **`statistics_values`** (EAV): `department, period_type(month|week), period_start, team_lead, metric_key, value, source(auto|manual|imported)`. UNIQUE по `(dept,ptype,period_start,coalesce(team_lead,''),metric)`. **R1**: тиждень→понеділок (лист=неділя, −6 днів). **R2**: «самостійні»+«Шевчук»→`team_lead='Шевчук Назар'` (sum сумуються, no-manager угоди→Шевчук).
- **`backend/src/statistics/catalog.ts`** — ЄДИНЕ джерело правди структури (відділи/метрики/unit/source/aggregation/csv-індекси/формули derived). Фронт і бекенд беруть перелік ЛИШЕ звідси. Планів тут НЕМА (R4 — план із `plans`).
- **Межа довіри `STATS_AUTO_FROM='2026-01-01'`**: до неї лист рахував МАШИНИ (одна угода=кілька машин), CRM рахує УГОДИ → числа непорівнянні, лишаємо imported. **Верифіковано (пробник 25 угод 2025): наша БД вже збігається з живим Kommo (усі 143), re-sync НЕ потрібен** — розрив 2025 це одиниці, не пропущені дані. Від 2026 одиниці збіглися → sales `revenue_won`/`machines_success`/`machines_dispatched` = auto. **Готівка (`cash_deals_amount`)** = auto від 2026 через ПРИХОД (`jobs/syncCashIncome`), НЕ бюджет (price занижує ~3×). Оплата/рахунки — imported (снапшот історично не відтворити).
- **dept-auto (marketing/logistics)**: `statistics/computeAuto.ts` + `DEPT_AUTO_ENABLED` (звірені ≤11% з листом): `marketing.non_target_leads`, `marketing.ad_budget_total`, `logistics.machines_dispatched_total`, `logistics.repeat_machines`, `logistics.repeat_revenue`. `ad_leads` (30% розбіжність — лист рахує ліди Кваліфікації) і канальні (lg_*) лишаються imported. Рівень відділу (team_lead=NULL). Живить `recomputeStatistics` (поточний період) + `backfillStatistics` (історія).
- **`jobs/recomputeStatistics`** — щогодини (:25) + старт: перераховує sales auto за поточний міс+тиждень, UPSERT. Guard+60с таймаут. Статус у `/api/health.statistics`.
- **`scripts/backfillStatistics.ts`** — одноразовий бекфіл (TRUNCATE+import листа+sales auto+звірка). Запуск вручну.
- **API `/api/statistics`**: `GET /catalog`, `GET /?department&period_type&from&to` (non-admin бачить лише свій розріз sales по команді), `PUT /manual` (лише admin; auto/derived→400). Скоуп sales: `team_id→team_lead` через `SALES_TEAM_LEAD`.
- Показник `calls` — джерело **Ringostat API LIVE per-manager** (`jobs/syncRingostatCalls`, щогодини :35 + старт; Auth-key у prod `.env` `RINGOSTAT_AUTH_KEY`). Поле **`employee_fio`** (ПІБ співробітника) кожного дзвінка → мапимо на нашого менеджера → тімліда (`buildLeadMap`/`resolveLead` по прізвищу+імені) → `sales.calls` ПО ТІМЛІДАХ. Результативні = **`billsec > 0`** (була розмова, як «Прийнятий» у ручному експорті). ⚠️ Мапимо по НАШІЙ структурі команд, НЕ по полю `department` Ringostat (воно ненадійне — той самий менеджер під іншим відділом). Рахуємо лише менеджерів команд продажу. Фронт `totalValue`: пріоритет per-lead sum. Історія (до поточного міс) — imported з листа/xlsx. Статус у `/api/health.ringostat`.

## Застряглі угоди — `/dashboard/stuck-deals`

Активні угоди повного циклу (`8921932`/`155304`, не `paid`) БЕЗ реальної людської активності за поріг. «Активність» = `deals.last_activity_at` (з `syncDealActivity`, нотатки/дзвінки з `created_by <> 0`) — НЕ `updated_at` (його бампить Salesbot). Fallback лише на `created_at` (Salesbot-proof). Пороги: грошові стадії (Авто працює `69716300/98470988/10937178`, Виставлено рахунок) ≥ minDays(7); рання «Взято в роботу» ≥ 3× (природний churn). Вікно створення 180 днів. Рання стадія рахується лише якщо угоду ВЖЕ вели (`last_activity_at IS NOT NULL`) — «нерозібрані» ліди це не «застрягли». Картка `StuckDealsCard` згорнута (клік «Показати»), top-50 по днях, `data-table.compact`. Показується per-manager (модалка менеджера у звіті) і per-team.

## Звіт КВП — `KvpReportSection`, тільки роль `admin` (=КВП)

Зведення керівника відділу продажу. Фронт реюзає `/dashboard/overview` + `/dashboard/lead-quality` для кожного періоду (цифри збігаються з рештою).
- **Динаміка (*) ЗАВЖДИ до аналогічного періоду минулого місяця**: місяць→минулий місяць; тиждень→той самий 7-денний блок минулого місяця.
- **Тижні місяця = фіксовані 7-денні блоки від 1-го**: `[1-7],[8-14],[15-21],[22-28],[29-кінець]` (`monthWeekBlocks`). «Поточний тиждень» = блок, у який попадає сьогодні (кліпнутий до сьогодні), порівнюється з тим самим блоком минулого місяця.
- Блоки: **За місяць** (поточний vs минулий) + декомпозиція + по командах; **Поточний тиждень** (vs аналог. тиждень мин. міс.); **Минулий місяць по тижнях** (тижні=колонки, +Разом).
- Рядки: дохід (отримані/успішно/оплата/сер.чек/нові/постійні/**перенесено з мин.міс.**), угоди+клієнти, реклама (**рекл.бюджет план/факт з `ad_budget_daily`**/GA-заявки/CRM-ліди/конверсія/**цільові**/**не цільові**), лідоген.
- **Цільові ліди** = пайплайн `8921932` створені в періоді; **не цільові** = Кваліфікація `8921928` статус `143` створені в періоді (`/lead-quality`).
- **Декомпозиція плану** (по відділу): треба авто = план ÷ ср.чек; треба лідів = авто ÷ конверсія; показує «вже»/«лишилось». ⏳ Розбивку РПК/РНК (групування команд) — коли буде відоме, яка команда до якої групи.
- Тендерний відділ ЗАКРИТО — тендерних рядків немає.

## Задачник KPI (тиждень/місяць)

Тімлід ставить план менеджеру (`POST /tasks/plan`): метрики `ads_count` (реклама google), `leadgen_count` (РПК), `dispatch_count` (поставлені авто — з подій входу в «Авто працює»), `avg_check`, `conversion`. **План = ОДНА задача-парасолька на період** (`task_type='kpi_period'`, `metrics_json` = підсумки періоду) + приховані діти-дні (`task_type='daily_kpi'`, `parent_id`, `metrics_json=[{metric,target,actual,done}]`). У списку видно ЛИШЕ парасольку; розкрити → дні з прогресом виконано/не виконано. Оцінює/ретаргетить дітей той самий движок (`evaluateKpiTasks`); парасолька→done, коли всі дні done (крок 6). Раніше дні були окремими задачами — тепер згруповані (не засмічують список). **Тижневий план — довільний період з календаря** (rangeFrom/rangeTo × дні тижня), НЕ фіксовані 7 днів. ⚠️ Дати в `/tasks` GET віддавати через `to_char(...,'YYYY-MM-DD')` (інакше DATE→timestamp і `<input type=date>` не показує → «дедлайн не зберігається»).
- **Тип «🔄 Реактивація клієнтів»** (тімлід/адмін): `GET /dashboard/reactivation-candidates` пропонує **лише компанії** (фізосіб НЕ пропонуємо), НЕ боржники, двох категорій: `lapsed` (3+ перевезень, замовкли >вікна) і `oneshot_bg` (компанія з 1 перевезенням = розрахунок б/г, прокладка доки нема поля «форма розрахунку» в CRM). Вибрані клієнти → **ОДНА задача на менеджера** з чеклістом (`task_type='reactivation'`, `checklist_json`), менеджер відмічає опрацьованих (`POST /tasks/reactivation`, тогл через `PATCH` checklistJson).
- **Департамент** призначається АВТОМАТИЧНО з команди виконавця при створенні (проста/KPI-денна задача); реактивація → «Реактивація».
- **Календар**: власний `components/DatePicker.tsx` (день/місяць, брендований поповер) замість нативних `<input type=date/month>` — у Звіті КВП, RepeatPlanGrid, PlansSection, формі плану задач. **«Сума» на день** = місячний план виручки (`plans.payment_amount`) ÷ робочі дні місяця (додається авто, якщо є план). `evaluateKpiTasks` заповнює факт по кожному показнику й закриває задачу, коли ВСІ виконані. Колонки в `tasks`: `task_type, metric, target_value, actual_value, plan_date, period_start/end, parent_id, auto, metrics_json`.
- **Бокова картка задачі** (drawer, клік 📄): усі поля (виконавець/дедлайн/департамент/пріоритет/статус, редаговані), повні коментарі (textarea), і для KPI — таблиця «Факт по показниках». Коментар у таблиці — textarea на повний текст.
- **Видимість**: менеджер — свої; тімлід — своя команда + власні (`created_by`, НЕ безхазяйні); адмін — вкладки «Мої» (створені мною, без виконавця) / «Усі». Фільтри: статус, виконавець, пошук.
